# Журнал архитектурных решений

> Формат: ADR-lite. Каждое решение — коротко: что, почему, альтернативы, последствия.
> Решения не удаляются. При отмене — помечаются `[ОТМЕНЕНО]` со ссылкой на новое.

## D-001. Avalonia UI вместо MAUI

**Дата:** 2026-09-26
**Статус:** принято

**Контекст.** Нужен кроссплатформенный UI для Windows, macOS, Linux, iOS, Android.

**Решение.** Avalonia UI 11.x + SkiaSharp.

**Почему.**
- Прямая работа со SkiaSharp — критично для быстрого рендеринга сотен камней.
- Единый XAML-опыт на всех платформах.
- Не требует macOS для сборки под macOS.

**Альтернативы.**
- .NET MAUI — медленнее, iOS/macOS через MAUI нестабильны.
- Uno Platform — тяжёлый, нишевый.

**Последствия.**
- Один UI-проект.
- Возможны проблемы со специфичными для платформ вещами (меню, иконки) — решаем точечно.

## D-002. Китайские правила вместо японских

**Дата:** 2026-09-26
**Статус:** принято

**Контекст.** Нужно выбрать правила подсчёта.

**Решение.** Китайские правила (area scoring), позиционное суперко.

**Почему.**
- Нет неоднозначностей с сэки и мёртвыми камнями.
- Суперко — единственное правило ко, не требующее отслеживания «немедленного» обратного захвата.
- Проще тестировать.

**Альтернативы.**
- Японские — сложнее, требуют соглашения о мёртвых камнях.
- ING — нишевые.

**Последствия.**
- Коми 7.5 на 19×19.
- Мёртвые камни не снимаются автоматически после двух пасов.

## D-003. MCTS без нейросети в v1

**Дата:** 2026-09-26
**Статус:** принято

**Контекст.** Реалистичная цель — 10 кю. 5 дан без нейросети недостижим.

**Решение.** В v1 — чистый MCTS с эвристиками. ONNX — в v2.

**Почему.**
- Чистый MCTS + pattern-based playout даёт 8–5 кю.
- Нейросеть требует bundle 50–200 МБ, что усложняет распространение.
- v1 должна быть рабочей и без сети.

**Последствия.**
- Целевой уровень v1: 30 кю – 10 кю.
- ONNX-модуль — отдельная фаза, после релиза v1.

## D-004. `record struct` для координат и значений

**Дата:** 2026-09-26
**Статус:** принято

**Контекст.** `Point`, `Move`, `Komi`, `Score` — мелкие value-типы, используются в горячих циклах.

**Решение.** `readonly record struct`.

**Почему.**
- Нет аллокаций в куче.
- Value equality из коробки.
- `with` для модификаций.

**Последствия.**
- `Point` не может быть `null`.
- `default(Point)` = `(0,0)` — валидная точка, следить за этим.

## D-005. Иммутабельный `Board` на публичном API

**Дата:** 2026-09-26
**Статус:** принято

**Контекст.** MCTS делает миллионы `ApplyMove` в секунду.

**Решение.** Публичный API `Board` иммутабелен. Внутреннее представление может быть мутабельным для скорости.

**Почему.**
- Иммутабельный публичный API — невозможно случайно испортить позицию.
- MCTS копирует позиции постоянно.
- Внутренняя мутабельность с `Clone()` — стандартный приём.

**Последствия.**
- `Board.ApplyMove(Move) → Board` (новый объект).
- Для MCTS: `Board.Clone()` + мутация на месте + `MakeMove` — быстрее.

**Альтернативы.**
- Полностью иммутабельный — медленнее в 2–3 раза.
- Полностью мутабельный — баги при копировании в MCTS.

## D-006. `Enumeration` вместо `enum`

**Дата:** 2026-09-26
**Статус:** принято

**Контекст.** Style Bible запрещает `enum` для статусов/типов.

**Решение.** `StoneColor`, `GameStatus`, `DifficultyLevel` — `Enumeration` по паттерну из Domain.

**Почему.**
- Единый стиль с остальным проектом.
- Возможность добавлять поля (например, `DifficultyLevel.RankKyu`).

**Последствия.**
- Больше кода, чем `enum`.
- Сравнение — по `Id` или по статическому экземпляру.

## D-007. `Enumeration`: реестр по статическим свойствам, равенство по типу и `Id`

**Дата:** 2026-09-26
**Статус:** принято

**Контекст.** `StoneColor` и `MoveType` — это `Enumeration`, но самого базового типа в проекте
не было. `AGENTS.md` п. 2 требует поля `Id`, `Name`, `Descriptions` и поиск `FromName<T>` /
`FromId<T>`. Style Bible п. 11 запрещает `public` поля, поэтому элементы нельзя объявить
статическими полями-константами.

**Решение.**
- Элементы объявляются публичными статическими **свойствами** (`StoneColor.Black { get; }`).
- Базовый тип строит реестр (`Items`, `ById`, `ByName`) рефлексией по публичным статическим
  свойствам своего типа. Кэш живёт во вложенном `Registry<T>`: рефлексия выполняется один раз на тип.
- Равенство — по типу и `Id`; реализован `IEquatable<Enumeration>` и операторы `==` / `!=`.
- `IComparable` **не реализован**.

**Почему.**
- Без `IComparable` равенство задаётся однозначно. Тест
  `Enumeration_Разные_Типы_С_Одинаковым_Идентификатором_Не_Равны` падал, пока база реализовывала
  `IComparable<Enumeration>`: xUnit предпочитает `IComparable<T>` и считал `StoneColor.Empty`
  (Id 0) равным `MoveType.Play` (Id 0), хотя `Equals` возвращал `false`.
- Сравнение «меньше/больше» между разными перечислениями смысла не имеет, а внутри одного
  перечисления сортировка доступна через `OrderBy(item => item.Id)`.

**Альтернативы.**
- Статические поля-константы — нарушают запрет `public` полей (Style Bible п. 11).
- `enum` — прямо запрещён Style Bible п. 11.
- `IComparable<Enumeration>` по одному `Id` — конфликтует с `Equals` и ломает утверждения тестов.
- Ручная регистрация элементов в каждом наследнике — дублирование и риск забыть элемент.

**Последствия.**
- Новый элемент достаточно объявить статическим свойством: реестр, `FromId` и `FromName`
  подхватят его сами.
- Поиск по имени — с учётом регистра (`StringComparer.Ordinal`); неизвестный `Id` или имя → `DomainException`.
- Рефлексия выполняется однократно на тип; в горячих путях (MCTS) её нет.

## D-008. Валидирующие value-типы: явный конструктор вместо позиционной записи

**Дата:** 2026-09-26
**Статус:** принято

**Контекст.** `BoardSize` по `AGENTS_GO.md` п. 2 — `readonly record struct`, а по T-001 он должен
принимать только 9, 13 и 19 и бросать `DomainException` на любом другом значении. Позиционная
запись `readonly record struct BoardSize(byte Value)` валидировать не может: её конструктор
генерирует компилятор.

**Решение.** `readonly record struct BoardSize` без позиционного списка: явный конструктор
`BoardSize(byte)`, свойство `Value { get; }` только для чтения, статические `Size9`, `Size13`, `Size19`.

**Почему.**
- Недопустимый размер нельзя получить ни через `new`, ни через `with`: свойство без `init`
  не участвует в `with`-инициализаторе.
- Тип остаётся `readonly record struct`: value equality из коробки, без аллокаций в куче.

**Альтернативы.**
- Позиционная запись плюс статические фабрики — `new BoardSize(10)` компилируется и не бросает.
- `Value { get; init; }` — `with { Value = 10 }` обходит валидацию.
- `enum` для размеров — запрещён Style Bible п. 11.

**Последствия.**
- Для будущих value-типов с инвариантами (`Komi`, `Score`) применяется тот же приём.
- `Point` и `Move` остаются позиционными: их поля проверяются не конструктором, а вызовом
  `IsOnBoard` в момент использования.

## D-009. Координатный формат `Point.ToString()`: номер строки считается сверху вниз

**Дата:** 2026-09-26
**Статус:** принято

**Контекст.** T-001 требует `Point.ToString()` в формате «D4» с буквами A…T без `I`.
`GO_RULES.md` п. 1 описывает внешний вид «цифры 1…19 снизу вверх», но у `ToString()` нет
параметра размера доски, а `y = 0` — это верхняя строка. Пересчёт «снизу вверх» без размера
доски невозможен.

**Решение.** `ToString()` возвращает букву столбца и `Y + 1`, то есть номер строки сверху вниз:
`default(Point)` → «A1». Отображение снизу вверх строится в слое App, где размер доски известен.

**Почему.**
- `ToString()` — техническое представление для отладочных сообщений и тестов; визуальные
  координаты — задача рендеринга.
- Формат «A1» для точки `(0,0)` соответствует имени теста `Point_ToString_19x19_Формат_A1`.
- Метод не бросает исключений: для `X` за пределами 19 столбцов возвращается «(x,y)».

**Альтернативы.**
- Перегрузка `ToString(BoardSize size)` — расширяет публичный API без требования задачи.
- Считать номер строки снизу вверх от 19 — неверно для досок 9×9 и 13×13.

**Последствия.**
- Если пользователь ожидает в `ToString()` вид «снизу вверх», меняется только этот метод
  и два теста `Point_ToString_19x19_*`.

## D-010. Два API хода: `ApplyMove` бросает `DomainException`, `IsLegal` возвращает `Result<Unit>`

**Дата:** 2026-09-26
**Статус:** принято

**Контекст.** Style Bible (п. 4) требует оформлять ожидаемые исходы — нелегальный ход, ко — через
`Result`, а не исключениями. T-001 закрепил в `Board.ApplyMove` исключение `DomainException`
на ход в занятую точку, а T-003 прямо требует `DomainException` с сообщением
«Самоубийственный ход» от `ApplyMove`. T-003 и T-009 при этом требуют `Board.IsLegal → Result<Unit>`.

**Решение.**
- `Board.ApplyMove` и `Board.MakeMove` — «доверенный» путь: ход либо выполняется, либо
  нарушение инварианта партии, о котором сообщает `DomainException` на русском языке.
- `Board.IsLegal(Move) → Result<Unit>` — «проверяющий» путь для AI и UI: тот же набор правил,
  но без исключений; причина отказа — в `Result.Error`.
- Обе дороги используют одну реализацию: `MakeMove` вызывает `CheckPlay` и превращает отказ
  в исключение, `IsLegal` возвращает его как `Result`.

**Почему.**
- `ApplyMove` уже был исключением в T-001, и это поведение закреплено тестами; менять его —
  ломать принятый контракт.
- AI должен перебирать ходы часто и не платить за исключения на каждом нелегальном ходе.
- Дублирования правил нет: проверка живёт в одном месте — `CheckPlay`.

**Альтернативы.**
- `ApplyMove → Result<Board>` — чище по Style Bible, но ломает T-001, T-002 и все их тесты.
- Только исключения — AI платит за них на каждом отфильтрованном ходе.

**Последствия.**
- Правило для `Core`: нелегальный ход в `ApplyMove`/`MakeMove` → `DomainException`;
  всё, что вызывается из AI в цикле, — через `IsLegal`.
- Самоубийство проверяется на копии доски (`Clone` + пробный ход): иначе пришлось бы
  дублировать снятие групп. Копия аллоцирует; при упоре в скорость в MCTS проверку
  можно переписать без копии, не меняя публичный API.
