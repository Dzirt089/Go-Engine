## D-001. Avalonia UI вместо MAUI

**Дата:** 2026-09-26
**Статус:** принято

**Контекст.** Нужен кроссплатформенный UI для Windows, macOS, Linux, iOS, Android.

**Решение.** Avalonia UI 11.x + SkiaSharp.

**Почему.**
- Прямая работа со SkiaSharp — критично для быстрого рендеринга сотен камней.
- Единый XAML-опыт на всех платформах.
- Не требует macOS для сборки под macOS.

**Альтернативы.**
- .NET MAUI — медленнее, iOS/macOS через MAUI нестабильны.
- Uno Platform — тяжёлый, нишевый.

**Последствия.**
- Один UI-проект.
- Возможны проблемы со специфичными для платформ вещами (меню, иконки) — решаем точечно.

## D-002. Китайские правила вместо японских

**Дата:** 2026-09-26
**Статус:** принято

**Контекст.** Нужно выбрать правила подсчёта.

**Решение.** Китайские правила (area scoring), позиционное суперко.

**Почему.**
- Нет неоднозначностей с сэки и мёртвыми камнями.
- Суперко — единственное правило ко, не требующее отслеживания «немедленного» обратного захвата.
- Проще тестировать.

**Альтернативы.**
- Японские — сложнее, требуют соглашения о мёртвых камнях.
- ING — нишевые.

**Последствия.**
- Коми 7.5 на 19×19.
- Мёртвые камни не снимаются автоматически после двух пасов.

## D-003. MCTS без нейросети в v1

**Дата:** 2026-09-26
**Статус:** принято

**Контекст.** Реалистичная цель — 10 кю. 5 дан без нейросети недостижим.

**Решение.** В v1 — чистый MCTS с эвристиками. ONNX — в v2.

**Почему.**
- Чистый MCTS + pattern-based playout даёт 8–5 кю.
- Нейросеть требует bundle 50–200 МБ, что усложняет распространение.
- v1 должна быть рабочей и без сети.

**Последствия.**
- Целевой уровень v1: 30 кю – 10 кю.
- ONNX-модуль — отдельная фаза, после релиза v1.

## D-004. `record struct` для координат и значений

**Дата:** 2026-09-26
**Статус:** принято

**Контекст.** `Point`, `Move`, `Komi`, `Score` — мелкие value-типы, используются в горячих циклах.

**Решение.** `readonly record struct`.

**Почему.**
- Нет аллокаций в куче.
- Value equality из коробки.
- `with` для модификаций.

**Последствия.**
- `Point` не может быть `null`.
- `default(Point)` = `(0,0)` — валидная точка, следить за этим.

## D-005. Иммутабельный `Board` на публичном API

**Дата:** 2026-09-26
**Статус:** принято

**Контекст.** MCTS делает миллионы `ApplyMove` в секунду.

**Решение.** Публичный API `Board` иммутабелен. Внутреннее представление может быть мутабельным для скорости.

**Почему.**
- Иммутабельный публичный API — невозможно случайно испортить позицию.
- MCTS копирует позиции постоянно.
- Внутренняя мутабельность с `Clone()` — стандартный приём.

**Последствия.**
- `Board.ApplyMove(Move) → Board` (новый объект).
- Для MCTS: `Board.Clone()` + мутация на месте + `MakeMove` — быстрее.

**Альтернативы.**
- Полностью иммутабельный — медленнее в 2–3 раза.
- Полностью мутабельный — баги при копировании в MCTS.

## D-007. `Enumeration`: реестр по статическим свойствам, равенство по типу и `Id`

**Дата:** 2026-09-26
**Статус:** принято

**Контекст.** `StoneColor` и `MoveType` — это `Enumeration`, но самого базового типа в проекте
не было. `AGENTS.md` п. 2 требует поля `Id`, `Name`, `Descriptions` и поиск `FromName<T>` /
`FromId<T>`. Style Bible п. 11 запрещает `public` поля, поэтому элементы нельзя объявить
статическими полями-константами.

**Решение.**
- Элементы объявляются публичными статическими **свойствами** (`StoneColor.Black { get; }`).
- Базовый тип строит реестр (`Items`, `ById`, `ByName`) рефлексией по публичным статическим
  свойствам своего типа. Кэш живёт во вложенном `Registry<T>`: рефлексия выполняется один раз на тип.
- Равенство — по типу и `Id`; реализован `IEquatable<Enumeration>` и операторы `==` / `!=`.
- `IComparable` **не реализован**.

**Почему.**
- Без `IComparable` равенство задаётся однозначно. Тест
  `Enumeration_Разные_Типы_С_Одинаковым_Идентификатором_Не_Равны` падал, пока база реализовывала
  `IComparable<Enumeration>`: xUnit предпочитает `IComparable<T>` и считал `StoneColor.Empty`
  (Id 0) равным `MoveType.Play` (Id 0), хотя `Equals` возвращал `false`.
- Сравнение «меньше/больше» между разными перечислениями смысла не имеет, а внутри одного
  перечисления сортировка доступна через `OrderBy(item => item.Id)`.

**Альтернативы.**
- Статические поля-константы — нарушают запрет `public` полей (Style Bible п. 11).
- `enum` — прямо запрещён Style Bible п. 11.
- `IComparable<Enumeration>` по одному `Id` — конфликтует с `Equals` и ломает утверждения тестов.
- Ручная регистрация элементов в каждом наследнике — дублирование и риск забыть элемент.

**Последствия.**
- Новый элемент достаточно объявить статическим свойством: реестр, `FromId` и `FromName`
  подхватят его сами.
- Поиск по имени — с учётом регистра (`StringComparer.Ordinal`); неизвестный `Id` или имя → `DomainException`.
- Рефлексия выполняется однократно на тип; в горячих путях (MCTS) её нет.

## D-008. Валидирующие value-типы: явный конструктор вместо позиционной записи

**Дата:** 2026-09-26
**Статус:** принято

**Контекст.** `BoardSize` по `AGENTS_GO.md` п. 2 — `readonly record struct`, а по T-001 он должен
принимать только 9, 13 и 19 и бросать `DomainException` на любом другом значении. Позиционная
запись `readonly record struct BoardSize(byte Value)` валидировать не может: её конструктор
генерирует компилятор.

**Решение.** `readonly record struct BoardSize` без позиционного списка: явный конструктор
`BoardSize(byte)`, свойство `Value { get; }` только для чтения, статические `Size9`, `Size13`, `Size19`.

**Почему.**
- Недопустимый размер нельзя получить ни через `new`, ни через `with`: свойство без `init`
  не участвует в `with`-инициализаторе.
- Тип остаётся `readonly record struct`: value equality из коробки, без аллокаций в куче.

**Альтернативы.**
- Позиционная запись плюс статические фабрики — `new BoardSize(10)` компилируется и не бросает.
- `Value { get; init; }` — `with { Value = 10 }` обходит валидацию.
- `enum` для размеров — запрещён Style Bible п. 11.

**Последствия.**
- Для будущих value-типов с инвариантами (`Komi`, `Score`) применяется тот же приём.
- `Point` и `Move` остаются позиционными: их поля проверяются не конструктором, а вызовом
  `IsOnBoard` в момент использования.

## D-009. Координатный формат `Point.ToString()`: номер строки считается сверху вниз

**Дата:** 2026-09-26
**Статус:** принято

**Контекст.** T-001 требует `Point.ToString()` в формате «D4» с буквами A…T без `I`.
`GO_RULES.md` п. 1 описывает внешний вид «цифры 1…19 снизу вверх», но у `ToString()` нет
параметра размера доски, а `y = 0` — это верхняя строка. Пересчёт «снизу вверх» без размера
доски невозможен.

**Решение.** `ToString()` возвращает букву столбца и `Y + 1`, то есть номер строки сверху вниз:
`default(Point)` → «A1». Отображение снизу вверх строится в слое App, где размер доски известен.

**Почему.**
- `ToString()` — техническое представление для отладочных сообщений и тестов; визуальные
  координаты — задача рендеринга.
- Формат «A1» для точки `(0,0)` соответствует имени теста `Point_ToString_19x19_Формат_A1`.
- Метод не бросает исключений: для `X` за пределами 19 столбцов возвращается «(x,y)».

**Альтернативы.**
- Перегрузка `ToString(BoardSize size)` — расширяет публичный API без требования задачи.
- Считать номер строки снизу вверх от 19 — неверно для досок 9×9 и 13×13.

**Последствия.**
- Если пользователь ожидает в `ToString()` вид «снизу вверх», меняется только этот метод
  и два теста `Point_ToString_19x19_*`.

## D-010. Два API хода: `ApplyMove` бросает `DomainException`, `IsLegal` возвращает `Result<Unit>`

**Дата:** 2026-09-26
**Статус:** принято

**Контекст.** Style Bible (п. 4) требует оформлять ожидаемые исходы — нелегальный ход, ко — через
`Result`, а не исключениями. T-001 закрепил в `Board.ApplyMove` исключение `DomainException`
на ход в занятую точку, а T-003 прямо требует `DomainException` с сообщением
«Самоубийственный ход» от `ApplyMove`. T-003 и T-009 при этом требуют `Board.IsLegal → Result<Unit>`.

**Решение.**
- `Board.ApplyMove` и `Board.MakeMove` — «доверенный» путь: ход либо выполняется, либо
  нарушение инварианта партии, о котором сообщает `DomainException` на русском языке.
- `Board.IsLegal(Move) → Result<Unit>` — «проверяющий» путь для AI и UI: тот же набор правил,
  но без исключений; причина отказа — в `Result.Error`.
- Обе дороги используют одну реализацию: `MakeMove` вызывает `CheckPlay` и превращает отказ
  в исключение, `IsLegal` возвращает его как `Result`.

**Почему.**
- `ApplyMove` уже был исключением в T-001, и это поведение закреплено тестами; менять его —
  ломать принятый контракт.
- AI должен перебирать ходы часто и не платить за исключения на каждом нелегальном ходе.
- Дублирования правил нет: проверка живёт в одном месте — `CheckPlay`.

**Альтернативы.**
- `ApplyMove → Result<Board>` — чище по Style Bible, но ломает T-001, T-002 и все их тесты.
- Только исключения — AI платит за них на каждом отфильтрованном ходе.

**Последствия.**
- Правило для `Core`: нелегальный ход в `ApplyMove`/`MakeMove` → `DomainException`;
  всё, что вызывается из AI в цикле, — через `IsLegal`.
- Самоубийство проверяется на копии доски (`Clone` + пробный ход): иначе пришлось бы
  дублировать снятие групп. Копия аллоцирует; при упоре в скорость в MCTS проверку
  можно переписать без копии, не меняя публичный API.

## D-011. Zobrist на SplitMix64 и общая история у копий доски

**Дата:** 2026-09-26
**Статус:** принято

**Контекст.** T-004 требует Zobrist-хеш позиции, «таблица генерируется один раз с фиксированным
seed для детерминизма», и отдельно — привязку истории к доске (`WithHistory`, `History`).
Копии доски создаются на каждом ходу (`ApplyMove`) и в MCTS (`Clone`).

**Решение.**
1. Таблица Zobrist заполняется SplitMix64 от постоянной константы, а не `System.Random`:
   алгоритм `Random` не гарантирован между версиями .NET, а хеши должны совпадать
   в тестах и в партии на любой машине.
2. Таблица — `ulong[2, 361]` (два цвета × максимальная доска 19×19); плоский индекс точки
   считается как `y * size + x`, поэтому одна таблица обслуживает все размеры доски.
3. `Board.Clone` и `Board.ApplyMove` передают копии **ту же** `PositionHistory`:
   это продолжение одной партии, а не новая. Доска без `WithHistory` имеет `History == null`.
4. `PositionHistory.Hashes` отдаёт снимок (`ToArray`): менять историю можно только через `Add`.

**Почему.**
- Детерминизм хеша — требование суперко: иначе повторение позиции не распознать.
- Пустая позиция даёт хеш 0 на любой доске: камней нет — складывать нечего.
- Общая история у копий избавляет от копирования истории на каждом ходу.
- Снимок вместо живой коллекции не даёт обойти `Add` через приведение типа.

**Альтернативы.**
- `Random(seed)` — проще, но результат зависит от реализации `System.Random`.
- `ulong[color, point]` на каждый размер доски — три таблицы вместо одной.
- Копирование истории в `Clone` — лишние аллокации на каждом ходу и расхождение историй.

**Последствия.**
- Анализ без суперко (MCTS-выборы, playout) делается на доске без истории: `History == null`,
  и проверка ко (T-005) такие доски пропускает.
- Смена зерна меняет все хеши: сохранённые где-либо хеши станут недействительны.
- Начальную позицию партии в историю добавляет тот, кто её создаёт (`GameState`, T-008):
  `Board` этого не делает, иначе первый ход в любую точку выглядел бы повторением.
- Позицию можно «примерить» без изменения доски и истории — `Board.PreviewMove` (internal):
  им пользуются проверка самоубийства (T-003) и `KoRule` (T-005).

## D-012. Сила уровня = доля случайности; MCTS подключается бюджетом playout'ов

**Дата:** 2026-09-26
**Статус:** принято

**Контекст.** T-012 требует три уровня (30, 25, 20 кю) с разной силой, T-017 — расширение
до 5 кю с MCTS, T-019 — статистическое доказательство, что слабый уровень проигрывает сильному.
Нужен один механизм, который даёт плавную шкалу силы.

**Решение.**
1. `DifficultyLevel` — `Enumeration` с полями `RankKyu`, `PlayoutBudget`, `RandomnessPercent`.
   `Id` уровня равен его рангу в кю (30, 25, 20, …), поэтому поиск `FromId` даёт уровень по рангу.
2. Сила уровня без MCTS задаётся долей случайности `RandomnessPercent`: 30 кю — 100%
   (чистый случай), 25 кю — 60%, 20 кю — 15%. Остальная доля ходов выбирается эвристиками.
3. Эвристики `HeuristicMoveSelector` идут по приоритету: съесть группу противника в атари
   (максимальный захват) → спасти свою группу в атари → занять угол в начале партии →
   случайный легальный ход.
4. `DifficultyLevel.CreateSelector(Random)` — единственная точка создания селектора по уровню;
   `Random` инжектируется снаружи (`AGENTS_GO.md`, п. 7).

**Почему.**
- Один числовой параметр даёт монотонную шкалу: больше кю — больше случайности — слабее игра.
- Эвристики «съесть/спасти атари» дают заметный скачок силы над чистым случаем, что и проверяет
  тест силы: Kyu20 выигрывает у Kyu30 не менее 55 партий из 100 на 9×9.
- Захват считается без копирования доски: группа снимается тогда и только тогда, когда её
  единственное дамэ — точка хода. Копия доски на каждый кандидат была бы в разы дороже.

**Альтернативы.**
- Отдельный класс на каждый уровень — дублирование и расхождение правил.
- Случайность только в «запасном» ходе (когда эвристики молчат) — уровни почти не различаются
  по силе, шкала получается ступенчатой.
- Оценка позиции по очкам вместо атари-эвристик — заметно дороже и требует `Scorer` в цикле.

**Последствия.**
- Для уровней 15 кю и сильнее (T-017) к шкале добавляется `PlayoutBudget`: MCTS-селектор
  получает и бюджет, и долю случайности.
- Тесты уровня обязаны фиксировать seed: при одном seed выбор детерминирован.

## D-013. Живучие playout'ы и быстрая проверка хода

**Дата:** 2026-09-26
**Статус:** принято

**Контекст.** Первый прогон MCTS показал две проблемы. Во-первых, случайный playout сам убивал
свои живые группы: политика закрывала собственные дамэ, включая глаза, и группа снималась
противником — оценка позиции получалась случайной. Во-вторых, ход проверялся на копии доски
(`Clone` + пробный ход), а playout делает десятки тысяч таких проверок.

**Решение.**
1. `PlayoutPolicy` отбрасывает ходы, после которых у своей группы меньше двух дамэ
   (`AtariHeuristics.LeavesOwnGroupInAtari`), а если таких ходов нет — пропускает ход (пас).
   Playout заканчивается на устоявшейся позиции, а не на доске, забитой камнями до отказа.
2. Захват в playout'ах ищется по группам противника в атари (один проход `AllGroups`),
   а не перебором всех ходов с оценкой каждого.
3. Ходы playout'а выбираются пробами случайных точек (`RandomAttempts` = 20) с откатом
   к полному перебору, если пробы не удались: так пас выдаётся только при полном отсутствии ходов.
4. `Board.IsLegal` проверяет самоубийство без копии доски: дамэ будущей своей группы считаются
   по пустым соседям точки и дамэ соседних групп. Копия строится только тогда, когда у доски есть
   история партии (для проверки суперко нужна позиция после хода целиком).
5. Ход выбирается по числу посещений, а при равенстве — по доле побед: при малом бюджете
   почти все корневые ходы получают по одному посещению, и выбор «первого» был бы случаен.

**Почему.**
- Без пункта 1 playout'ы давали противоположные оценки: после снятия 9 камней чёрные
  выигрывали 1 playout из 10, потому что сами забивали свой глаз. После правки — 10 из 10.
- Пункт 2 убирает сотни вызовов `FindGroup` на каждый ход playout'а.
- Пункт 4 ускоряет проверку хода примерно втрое и не меняет правила: тесты T-001–T-008
  прошли без изменений.

**Последствия.**
- Один playout на 9×9 занимает около 20 мс. Бюджет 5000 playout'ов из `MctsConfig.Default`

## D-017. Бюджет MCTS по времени и протокол замера силы серии T-019

**Дата:** 2026-09-26
**Статус:** принято (T-019a)

**Контекст.** T-019a требует, чтобы MCTS думал «T миллисекунд», а не «N playout'ов»: тогда сила
не зависит от скорости машины. Одновременно серия T-019a…T-019e требует после каждой задачи
замер силы, а метрика D-016 («≥ 7 из 10 при 1000 мс на ход») на этом движке неисполнима
по времени: пропускная способность — **92 playout/с** на позиции середины партии, то есть
одна партия при 1000 мс на ход занимает около пяти минут, а матч из десяти — около часа.

**Решение.**
1. `MctsConfig` задаёт бюджет ровно одним способом: число playout'ов (детерминированные тесты
   и замеры) или время на ход (игра). Оба сразу или ни одного — `DomainException`.
   `DefaultForSize`: 9×9 — 2000 мс, 13×13 — 4000 мс, 19×19 — 6000 мс.
2. Время берётся только через `TimeProvider` (`AGENTS.md`, п. 6); в тестах — `FakeTimeProvider`
   из `Microsoft.Extensions.TimeProvider.Testing`.
3. Уровни 10/8/5 кю думают по времени (1/2/3 с на ход); уровень 15 кю остаётся на playout'ах —
   он эталон для замеров серии, и замеры должны быть воспроизводимы.
4. **Протокол замера серии** (отклонение от D-016 по времени, но не по смыслу):
   - матч: 10 полных партий на 9×9, коми 5.5, цвета чередуются, зерно `20260926 + i`;
   - испытуемый: MCTS с бюджетом 6 playout'ов на ход без случайности;
   - соперник: `Kyu20` (эвристики, 15 % случайности) — ближайший слабый уровень лестницы;
   - тактика: 5 цумэго из `TsumegoPositions` тем же селектором;
   - скорость: playout'ов в секунду на позиции `BlockInAtari` при бюджете 500 мс;
   - стенд один на всю серию — `StrengthBenchmark` в тестах.

**Таблица «версия → сила» (замер по протоколу выше):**

| Версия | Матч против Kyu20 | Цумэго | Пропускная способность | Оценка силы |
|---|---|---|---|---|
| v1 random-playout | 4/10 | 5/5 | 92 playout/с | ~20 кю |
| v2 eye-safe | 5/10 | 5/5 | 68 playout/с | ~20 кю |
| v3 паттерны (веса вкл.) | 2/10 | 5/5 | 76 playout/с | ~20 кю |
| v3 паттерны (веса выкл.) | 2/10 | 5/5 | 90 playout/с | ~20 кю |
| v4 RAVE | 2/10 | 5/5 | не измерялась | ~20 кю |

**Последствия.**
- Матч уровня «6 playout'ов» против Kyu20 укладывается в минуты, поэтому серия может мерить
  каждую версию после каждой задачи.
- MCTS проигрывает эвристическому уровню 20 кю: тактика цумэго решается, а полная партия — нет.
  Именно это и должна исправить серия.

## D-018. Eye-safe playout: глаза не заполняются, вынужденный ход — только безопасный

**Дата:** 2026-09-26
**Статус:** принято (T-019b)

**Контекст.** T-019b требует, чтобы playout не заполнял собственные глаза: без этого он сам
убивает свои живые группы. Требование к глазам — «все соседи по стороне свои плюс норма
диагоналей: в углу 1, на краю 2, в центре 3»; вынужденный ход (когда остались только глаза)
разрешён. Серия требует замера после каждой задачи.

**Что сделано.**
1. `EyeDetector.IsEye(Board, Point, StoneColor)` — настоящий глаз с обязательной диагональной
   проверкой: без неё ложные глаза (2 диагонали из 4 в центре) считались бы глазами.
2. `PlayoutPolicy` исключает свои глаза из кандидатов; `PlayoutConfig.EyeSafe` (по умолчанию
   `true`) позволяет отключить проверку для A/B-замеров.
3. Вынужденный ход: если безопасных ходов нет, разрешается заполнить глаз — но только такой,
   который не оставляет свою группу в атари.

**Что измерено (9×9, 6 playout'ов на ход, 10 партий, протокол D-017):**

| Версия | Против предыдущей | Против Kyu20 | Цумэго | Пропускная способность |
|---|---|---|---|---|
| v1 random-playout | — | 4/10 | 5/5 | 92 playout/с |
| v2 eye-safe | **6/10** | **5/10** | 5/5 | 68 playout/с |

**Три варианта вынужденного хода (замеры, из-за которых принят третий):**

| Вынужденный ход | Цумэго | Тесты T-016 | Пропускная способность |
|---|---|---|---|
| любой легальный, включая ходы «в атари» | 2/5 | 2 теста падают | 60 playout/с |
| только собственные глаза (в том числе в атари) | 3/5 | 3 теста падают | 76 playout/с |
| **любой безопасный (не в атари), глаз разрешён** | **5/5** | все зелёные | 68 playout/с |
| без вынужденного хода (пас) — поведение v1 | 5/5 | все зелёные | 92 playout/с |

**Вывод.** Eye-safe даёт небольшой, но воспроизводимый перевес: 6 из 10 против прежней политики
и +1 победа против Kyu20. Разрушительными оказались именно ходы «в атари»: как только вынужденный
ход их допускает, тактика падает с 5/5 до 2–3/5 и ломаются тесты T-016. Поэтому вынужденный ход
ограничен безопасными ходами — это отличается от буквальной формулировки задачи
(«разрешить заполнить глаз»), но подтверждено замерами.

**Последствия.**
- Пропускная способность упала с 92 до 68 playout/с: playout'ы стали длиннее, потому что
  в конце партии они доигрывают до счёта, а не останавливаются пасом. При 6 playout'ах на ход
  это не критично, но при бюджете по времени даёт меньше симуляций.
- Сила выросла незначительно: eye-safe — необходимое, но не достаточное условие. Основную
  отдачу серия ожидает от T-019c (паттерны) и T-019d (RAVE).

## D-019. Паттерновая политика: классы фигур и веса 3×3 не дают силы, по умолчанию выключены

**Дата:** 2026-09-26
**Статус:** принято с оговоркой (T-019c → `closed_with_caveats`)

**Контекст.** T-019c требует заменить «случайность плюс пара эвристик» на политику,
приоритизированную по 3×3-паттернам с классами ходов: захват атари, спасение атари,
блокировка глаза противника, разрезание, продление, вес фигуры, случайный ход.

**Что сделано.**
1. `Pattern3x3` — код из девяти клеток по два бита, канонизация по восьми симметриям
   (повороты и отражение): одна и та же фигура в любом повороте имеет один вес.
2. `PatternWeights` — ручная таблица фигур (hane, nobi, cut, atari, блокировка глаза,
   первая линия, ход в пустоту) со значениями 0.1…1.0 и весом по умолчанию 0.5.
   Точные таблицы GNU Go не переносились: у них другая структура паттернов.
3. `PatternPolicy` — классы ходов и взвешенно-случайный выбор; `PlayoutPolicy` делегирует ей.
4. Настройки `PlayoutConfig.AggressiveShapes` и `PlayoutConfig.Patterns` включают агрессивные
   классы и веса; по умолчанию обе выключены.

**Что измерено (9×9, 6 playout'ов на ход, 10 партий, протокол D-017):**

| Вариант v3 | Против Kyu20 | Цумэго | Пропускная способность |
|---|---|---|---|
| полная лестница классов и веса | 3/10 | 5/5 | 28 playout/с |
| агрессивные классы выключены | 4/10 | 5/5 | 38 playout/с |
| дешёвый отбор кандидатов, веса включены | 2/10 | 5/5 | 76 playout/с |
| веса выключены (поведение близко к v2) | 2/10 | 5/5 | 90 playout/с |

**Вывод.** Ни один вариант не дал роста силы: разброс 2–4 победы против 5 у v2. Разница в 2–3
победы на десяти партиях лежит внутри статистического шума (при вероятности 0.3–0.5 одно
стандартное отклонение — около 1.5 победы), но ни один замер не превысил уровень v2, поэтому
ручные веса и агрессивные классы выключены по умолчанию, а не «подкручены» под результат.
Побочный результат: дешёвый отбор кандидатов ускорил playout'ы до 90 в секунду — быстрее,
чем у v1 (92 при другой политике) и заметно быстрее v2 (68).

**Почему паттерны не помогли.** Ручные веса поощряют контактную борьбу (hane, разрезание,
вторжение в глазное пространство). В playout'е, который доигрывает партию до счёта по площади,
такие ходы отдают темп и территорию: борьба не успевает принести очки до конца симуляции.

**Последствия.**
- Паттерновая машинерия остаётся в коде и покрыта тестами; включение — одна настройка.
- Следующая задача серии (T-019d, RAVE) меняет не политику, а статистику выбора хода —
  это другой рычаг, и он не зависит от неудачи паттернов.

## D-020. RAVE: поправка на статистику всех симуляций — нейтрально при шести playout'ах

**Дата:** 2026-09-26
**Статус:** принято (T-019d)

**Контекст.** T-019d требует RAVE: ход получает статистику не только со своего пути в дереве,
но и из всех симуляций, где он встречался. Формула: β = √(k / (3n + k)), оценка
(1−β)·Q + β·Q_rave + c·√(ln N / n), постоянная k = 1000.

**Что сделано.**
1. `MctsNode`: `RaveVisits`, `RaveWins`, `RaveBeta(raveK)`, `Ucb1Rave(c, raveK)`.
   Узлы хранят RAVE-статистику скалярами: она нужна родителю при выборе ребёнка.
2. `MctsTree.Backpropagate(node, winner, playedMoves)` — обычные посещения идут по пути спуска,
   RAVE-посещения получают все дети этого пути, чей ход встретился в симуляции (AMAF).
   Перегрузка без списка ходов оставлена для тестов и отключает RAVE.
3. `MctsConfig.RaveK` (по умолчанию 1000) задаётся через `with`; 0 отключает поправку
   и возвращает обычный UCB1.
4. `MctsMoveSelector` собирает ходы симуляции и передаёт их в `Backpropagate`.

**Что измерено (9×9, 6 playout'ов на ход, 10 партий, протокол D-017):**

| Сравнение | Результат |
|---|---|
| RAVE включён против RAVE выключен | 5/10 — ровно пополам |
| RAVE против Kyu20 | 2/10 |
| Цумэго | 5/5 |

**Вывод.** При бюджете в шесть playout'ов RAVE не меняет силу: 5 из 10 в прямом сравнении.
Это ожидаемо: поправка выигрывает там, где посещений много (β падает с ростом n), а при шести
симуляциях она либо нейтральна, либо шумна. Поправка оставлена включённой по умолчанию
как стандартный приём MCTS и отключается одной настройкой.

**Последствия.**
- Тест `Rave_Не_Ломает_Обычный_UCB1_При_K∞` переименован в
  `Rave_Не_Ломает_Обычный_UCB1_При_Нулевой_Постоянной`: символ ∞ недопустим в имени метода C#.
- RAVE добавляет работу на каждую симуляцию (построение множества ходов и обход детей пути),
  поэтому его польза проявится только вместе с большим бюджетом playout'ов.

## D-025. Анализаторы Roslyn и единая команда проверки

**Дата:** 2026-09-26
**Статус:** принято (структурная причёска, ступень 2)

**Контекст.** Ступень 1 дала структуру и правила стиля. Дальше нужны две вещи, без которых
структура держится только на дисциплине: автоматическая проверка качества кода и одна команда,
которой проект проверяется целиком.

**Решение.**
1. `AnalysisMode=Recommended` в `Directory.Build.props`: анализаторы Roslyn включены для всех
   проектов, а `TreatWarningsAsErrors` делает их замечания ошибками сборки.
2. `check.ps1` и `check.sh` — единая проверка: сборка решения, оба тестовых проекта и восемь
   режимов приложения (`--smoke`, `--check`, `--state`, `--settings`, `--sgf`, `--animation`,
   `--e2e`, `--stress`). Флаг `--skip-stress` пропускает проверку нагрузки.
3. Раздел «Как проверять проект» в `PROJECT.md` описывает команды и режимы.

**Что это дало.** Рекомендуемый набор нашёл шесть замечаний. Два оказались настоящими
находками и исправлены в коде, четыре конфликтуют с формами API, зафиксированными задачами;
разбор каждого — в D-026. Сборка после разбора зелёная, предупреждений нет.

**Почему одна команда.** Раньше проверка состояла из тестов и ручного перебора режимов
приложения; теперь «definition of done» — это одна команда, и её же будет вызывать будущий CI.

**Последствия.** Любое новое правило анализатора сразу становится требованием сборки. Если
понадобится ослабить конкретное правило, это делается точечно в `.editorconfig` с объяснением,
а не отключением анализаторов целиком.

## D-029. Файл решения: папки, только Any CPU; версия SDK зафиксирована

**Дата:** 2026-09-26
**Статус:** принято (структурная причёска, ступень 6)

**Контекст.** `GoEngine.sln` собрался из `dotnet new sln` и шести `dotnet sln add`: проекты
в перемешку (Core, Tests, AI, App, App.Tests, AI.Onnx), у каждого три платформы — `Any CPU`,
`x64`, `x86` — то есть шестьдесят строк настроек, которых ни один скрипт не использует
(`build.ps1` и `check.ps1` платформу не задают). Папок в обозревателе решений нет, а версия
SDK нигде не объявлена: сборка зависит от того, что стоит в системе.

**Решение.**
1. Проекты в файле решения идут слоями: `Core` → `AI` → `AI.Onnx` → `App` → `Tests` →
   `App.Tests`. Порядок чтения файла совпадает с порядком зависимостей.
2. Две папки решения — `src` (четыре проекта) и `tests` (два): та же граница, что и на диске.
3. Конфигурации — только `Debug|Any CPU` и `Release|Any CPU`. Проверено: ни один скрипт
   платформу не задаёт, а сборки под три системы идут через `-r <rid>`, а не через платформу.
4. `global.json`: SDK 8.0.100 и `rollForward: latestMajor`. Проект объявляет .NET 8 как
   минимум, собирается и на более новом SDK (локально 10.0.400, на агенте 8.0.x).
5. `ContinuousIntegrationBuild` включается при `CI=true` — пути в артефактах детерминированы,
   локальная отладка при этом не страдает.

**Альтернативы.** Оставить файл решения как сгенерировал `dotnet sln add` — отклонено: шум
в настройках и отсутствие порядка читаются как небрежность. Прописать точный SDK без
`rollForward` — отклонено: сломало бы сборку на машине, где .NET 8 SDK не установлен.

**Последствия.** Обозреватель решений показывает слои, а не плоский список. Оговорка:
`dotnet sln add` для нового проекта снова добавит `x64`/`x86` — эти строки нужно убирать
руками, правило записано здесь.

   `OnnxEvaluation`: вероятности ходов (мягкий максимум логитов первого канала), вероятность
   победы (мягкий максимум трёх логитов `value`), индекс паса и лучший ход. Ожидаемые отказы —
   `Result`, отсутствие нужного выхода в модели — `DomainException`.
4. Раскладка признаков сверена с конвертером, которым собрана модель
   (`kaya-go/katago-onnx`, `src/katago/game/features.py`), и исправлена:
   коми делится на **20**, а не на 15; «пас завершит партию» — признак **14**, а не 12;
   волна чётности коми — признак **18**, а не 13; признаки 8…13, 15…17 у нас нули, потому что
   соответствующих правил (самоубийство, территория, налоги, encore, асимметричные степени
   двойки, «кнопка») в движке нет. Пространственные 22 плоскости совпали с уже реализованной
   раскладкой, менять их не пришлось.

**Что проверено на настоящей модели** (тесты `OnnxModelTests`, 9 штук): первый ход на пустой
доске — угол третьей-четвёртой линии (звёздные точки и 3-4 пункты, пас меньше 1 %); перевес
в 20 камней даёт победную вероятность больше 0,9 за сильную сторону и меньше 0,1 за слабую;
рост коми уменьшает шансы чёрных; доска 9×9 отвергается; вероятности ходов нормированы.

**Что осталось приблизительным — сознательно.**
- Лестничные плоскости 14…17 — нули: лестничные признаки не считаются (как и было в T-032).
- Плоскость 6 заполняется запретами позиционного суперко движка, а у конвертера там «простой ко»:
  расхождение только в редких позициях с повторением.
- Модель квантована динамически в uint8 — это самый быстрый и самый неточный из трёх вариантов
  в репозитории (есть `.fp32` и `.fp16`), выбрана по указанию пользователя.
- Модель не обучена на наших правилах подачи коми в точности: на пустой доске при коми 0 она
  считает позицию ходящего выигранной на ~92 %, что для Го неправдоподобно. На материальный
  перевес и на изменение коми она реагирует правильно, поэтому для MCTS этого достаточно,
  но паспортной силы ждать не стоит: сила измеряется отдельно (T-033, продолжение).

**Альтернативы.** Взять `.fp32` — точнее, но вчетверо больше и медленнее; оставлено на случай,
если замер силы упрётся в качество оценки. Взять вторую модель из того же репозитория
(`kata1-b28c512nbt-s12043015936-d5616446734`) — та же архитектура, отличается обучением;
запасной вариант, если первая не даст силы.

**Последствия.** Блокер T-033 снят. Модель у каждого своя: без неё тесты модели помечаются
пропущенными (`ModelFactAttribute`), поэтому `check.ps1` и будущий CI остаются зелёными
и на машине без модели. Дальше — подключить оценку к MCTS (приоритеты из политики, оценка
вместо случайного playout'а) и замерить силу по протоколу D-017.

## D-034. MCTS с оценкой сети: политика задаёт порядок разбора, оценка заменяет playout

**Дата:** 2026-09-27
**Статус:** принято (T-033, шаг 4)

**Контекст.** Сеть подключена (`OnnxEvaluator`), но поиск её не использовал: MCTS играл
случайные playout'ы (D-021 — потолок такой игры 20–15 кю). Нужно, чтобы сеть влияла на поиск:
политика подсказывает, какие ходы проверять первыми, оценка позиции заменяет доигрывание партии.

**Решение.**
1. Порт `IPositionEvaluator` объявлен в слое `AI`, реализация — `OnnxEvaluator` в `AI.Onnx`:
   движок не зависит от ONNX Runtime (AGENTS.md, раздел 1). Порт возвращает не `Result`,
   а оценку или исключение `AiException`: отказ сети посреди тысячи итераций — ошибка настройки,
   а не ожидаемый исход (сравни D-024, где `Result` уместен на границе файлов).
2. `OnnxEvaluation` переводится в `PositionEvaluation`: вероятности ходов и вероятность победы
   ходящего, обе посчитаны мягким максимумом логитов модели.
3. Поиск с оценкой за одну итерацию делает один вызов сети: получает исход позиции (его берёт
   путь до корня) и вероятности ходов (их берёт новый ребёнок). Дерево выбирает ребёнка по PUCT
   (`Q + c·P·√N/(1+n)`), а не по UCB1 с RAVE.
4. Порядок разбора ходов задаёт политика сети (`BestUntriedMove`), а не порядок списка легальных
   ходов. Без этого при малом бюджете разбирались бы произвольные ходы, и сеть влияла бы только
   на выбор среди уже разобранных.
5. `MctsNode.Puct` намеренно **не** даёт непосещённому узлу бесконечность (в отличие от
   `Ucb1`): иначе поиск обязан перебрать все ходы подряд, и приоритеты ничего не решают.
   Пока посещений нет, узлы различает только мнение сети.
6. Оценка вероятностная, поэтому `MctsNode.RegisterResult` принимает долю от 0 до 1: узел
   получает оценку «за своего» как есть, соперник — как `1 − оценка`. Результат партии из
   playout'а приходит сюда же как 1 или 0, поэтому обе ветки поиска считаются одинаково.

**Альтернативы.** Оставить UCB1 с RAVE и добавить приоритет отдельным слагаемым — отклонено:
RAVE набирает статистику по случайным playout'ам, которых при игре с сетью нет. Считать оценку
на каждом спуске — отклонено: один вызов сети на узел вместо одного на итерацию, а сеть здесь
самое дорогое. Дирихле-шум и FPU (как в AlphaZero) — не нужны: шум служит разнообразию
состязательной игры, а движку нужен один сильный ход.

**Последствия.** Уровни 15–5 кю могут играть с сетью: селектор принимает оценку необязательным
параметром, без неё поведение прежнее. Что осталось: подключить сеть к уровням (`AiFactory`,
ссылка `App` → `AI.Onnx`) и замерить силу по протоколу D-017.

**Проверено отдельно: размер доски.** Вход модели объявляет высоту и ширину динамическими
(`−1`), поэтому признаки и оценка теперь считаются для любой доски. Верить этой оценке можно
только на 19×19: на 9×9 сеть предлагает первый ход F4 и даёт чёрным 87 % при коми 5,5 — этого
не может быть ни по теории, ни по её же оценке на 19×19. Причина понятна: модель обучена
на 19×19, и малая доска для неё вне обучающего распределения.

**Следствие для замера силы.** Протокол D-017 (10 партий на 9×9, seed 20260926) для игры
с сетью не подходит. Замер силы сети идёт на 19×19, а сравнивать его с прежней таблицей версий
(она на 9×9) напрямую нельзя — нужна отдельная серия на своей доске и своём бюджете, иначе
числа будут про разное. Бюджет также придётся считать в итерациях поиска, а не в playout'ах:
одна итерация с сетью — это один вызов модели.

## D-035. GitHub как второй origin, CI на двух системах и релиз под четыре платформы

**Дата:** 2026-09-27
**Статус:** принято

**Контекст.** Проект лежал только в локальном bare-репозитории: публичного зеркала не было,
потому что репозитории не создаются без аутентификации, а `gh` в системе не установлен
(`GIT.md`). Пользователь создал репозиторий `github.com/Dzirt089/Go-Engine` и попросил
сохранить проект там, а также сделать CI/CD с публикацией релизов под Windows, Linux, macOS
и Android.

**Решение.**
1. `github` — второй remote рядом с локальным `origin`: `origin` остаётся рабочей копией
   истории, `github` — публикация. Force-push в `main` по-прежнему запрещён.
2. `ci.yml` проверяет проект на **двух** системах: Linux (`check.sh`) и Windows
   (`check.ps1 -SkipStress`). Приложение настольное, и ломается оно на системах по-разному;
   одна Linux-проверка этого не ловит.
3. `release.yml` запускается по тегу `v*` или вручную (тогда тег и признак «черновик»
   задаёт человек). Сначала обязательная проверка проекта: релиз не собирается из красного
   коммита. Затем матрица самодостаточных сборок `win-x64`, `linux-x64`, `osx-x64`,
   `osx-arm64` (каждая проверяется запуском `--smoke` и упаковывается в zip или tar.gz)
   и APK для Android. Последняя задача создаёт релиз через `gh release create` с готовыми
   заметками — без сторонних действий, только официальный CLI.
4. Интерфейс разделён на общий вид и головы: `Views/BoardView` (доска, панель статуса,
   отмена и возврат) используют и окно `MainWindow` (плюс меню, настройки, файлы), и
   `GoEngine.App.Android` (один вид без меню). `App.OnFrameworkInitializationCompleted`
   выбирает вид по жизненному циклу: настольный или единственный.
5. Проект `GoEngine.App.Android` намеренно **не входит** в `GoEngine.sln`: его сборка требует
   рабочей нагрузки `android` (`dotnet workload install android`), которой нет у того, кто
   собирает настольную версию. Локальная проверка (`check.ps1`) остаётся быстрой, а Android
   собирается в CI, где SDK восьмой и нагрузка ставится явно.

**Почему APK без подписи.** Ключ подписи — секрет пользователя; в репозиторий он не попадает.
CI собирает APK в режиме по умолчанию (без `AndroidKeyStore`), то есть файл для проверки,
а не для магазина. Когда появится ключ, он добавляется секретами и шаг подписи включается
без переделки workflow.

**Последствия.** Публикация релиза — тег или кнопка в Actions. Артефакты: три настольные
системы (macOS двумя архитектурами) и Android. Осталось на будущее: подпись APK своим ключом,
iOS (нужна голова `GoEngine.App.iOS` и macOS-раннер с сертификатами), установщики вместо
архивов (MSI, dmg, deb).

## D-036. Интерфейс — библиотека, платформы — головы

**Дата:** 2026-09-27
**Статус:** принято (правка структуры, чтобы Android собирался)

**Контекст.** Сборка APK падала: голова Android не видела типы из `GoEngine.App`. Сначала
казалось, что дело в исполняемом проекте, но настоящая причина оказалась другой и обиднее:
при записи файлов проектов съелись обратные слэши в путях, и ссылка вела в никуда
(`..GoEngine.AppGoEngine.App.csproj`). Заодно выяснилось, что раскладка была не та, что нужна
многоплатформенному приложению: интерфейс лежал в исполняемом проекте вместе с точкой входа.

**Решение.**
1. `GoEngine.App` — **библиотека**: виды (`BoardView`, `MainWindow`, `SettingsWindow`),
   модель представления, сервисы, рисование, `App`. Пакет `Avalonia.Desktop` из неё убран
   (он платформенный), добавлен `Avalonia.Skia` — им рисует `BoardControl`.
2. `GoEngine.App.Desktop` — голова: `Program.cs` и `Diagnostics` (проверочные режимы),
   `WinExe`, `Avalonia.Desktop`, манифест. Имя сборки — `GoEngine.App.Desktop`.
3. `GoEngine.App.Android` — голова: `MainActivity`, тема, манифест; берёт общий `App`
   из библиотеки.
4. Пути ссылок в файлах проектов записаны через прямой слэш: MSBuild понимает и его,
   а испортить такой путь случайным экранированием нельзя.

**Урок на будущее.** Файлы с путями Windows пишутся прямым слэшем и проверяются чтением
или поиском по шаблону ссылки — сборка такое ловит не сразу и не там, где причина.

**Последствия.** Один и тот же `BoardView` работает и в окне, и на телефоне; мобильная
сборка больше не тянет настольные пакеты. Релизный прогон CI зелёный целиком, черновик
релиза `v0.1.0` содержит шесть файлов: APK (подписанный отладочным ключом), zip для Windows
и три tar.gz (Linux, macOS двух архитектур). Точка входа настольной версии переименована,
поэтому скрипты и workflow переведены на `GoEngine.App.Desktop`.

## D-038. Разделение зон ответственности AI по размеру доски

**Дата:** 2026-09-27
**Статус:** принято (задача T-034)

**Контекст.** Обычный MCTS (до 10 кю) настраивался и измерялся на доске 9×9, на 19×19 он играет
слабо из-за нехватки бюджета. Нейросетевая модель KataGo обучалась на 19×19; на 9×9 её оценка
неправдоподобна (D-034).

**Решение.**
1. Ввести жёсткое разделение зон ответственности: нейросеть (уровни Дан) работает **только**
   на досках 19×19 и 13×13.
2. Чистый MCTS (уровни Кю) доступен на всех досках, но является основным для 9×9.
3. На уровне `AiFactory` попытка запросить уровень с нейросетью для доски 9×9 вызывает
   `DomainException`.
4. На уровне интерфейса при выборе доски 9×9 уровни Дан скрываются, а текущий выбор сбрасывается
   до 10 кю.

**Почему.** Переобучать сеть под 9×9 или раздувать бюджет MCTS для 19×19 — вне рамок текущего
проекта (offline-first). Архитектурное ограничение честно отражает возможности алгоритмов
и защищает пользователя от неадекватной игры AI.

**Последствия.** Появляются уровни Дан — они возможны только с загруженной моделью и только
на больших досках; без модели уровни Дан недоступны в интерфейсе, а уровни Кю работают как
прежде на любом размере.

**Реализовано (T-034).**
1. `SelectorKind.Neural` и уровень `Dan5` (ранг −5, две секунды на ход, без случайности) плюс
   признак `DifficultyLevel.NeedsNetwork`.
2. `AiFactory.Create` принимает размер доски и оценку и отказывает `DomainException` в трёх
   случаях: уровень с сетью на 9×9, без размера доски, без модели.
3. Библиотека интерфейса осталась без зависимости от ONNX: оценщик передаётся через
   `App.Evaluator`, который задаёт голова; `GoEngine.App.Desktop` ищет файл модели вверх
   от каталога сборки, грузит его и кладёт в эту точку. `MainViewModel` принимает оценщик
   и размер доски, а уровень Дан без модели или на 9×9 заменяет на 10 кю.
4. `LevelChooser` (сервис интерфейса) перечисляет доступные уровни для доски, сбрасывает
   недоступный выбор на 10 кю и собирает подписи «N кю» / «N дан»; диалог настроек строит
   список через него и перестраивает при смене размера доски.

Проверка: `check.ps1` — «всё зелёное», 471 тест в `GoEngine.Tests` и 24 в `GoEngine.App.Tests`
(12 тестов добавлено по этой задаче). Коммиты `bb0bc45`, `43023e7`, `03b1828`.

---

**Итог серии замеров T-033 (полный протокол, 10 партий каждый матч):** против эвристики
`Kyu20` — **10 из 10**, против обычного MCTS `Kyu10` — **10 из 10**. Матч против `Kyu10`
во втором прогоне дал те же 10 побед с ещё большим запасом: 125:23,5, 129,5:10, 124:20,5,
125,5:15, 135:14,5, 126,5:14, 122:13,5, 126,5:20, 124:16,5, 129,5:12. Разброс объясним:
обычный MCTS на 19×19 не успевает доиграть партию до счёта, поэтому проигрывает крупно. Ни одна версия серии
T-019a…T-019e не давала больше 5 из 10 (D-021). Заявка «уровень 5 кю» пока не проверена:
для неё нужен соперник заведомо сильнее 10 кю, которого в проекте нет — ни среди уровней,
ни среди внешних программ (offline-first).

**Что этот замер доказывает и чего не доказывает.** Доказывает: сеть с поиском уверенно сильнее
эвристики 20 кю — это первый случай в проекте, когда версия обошла соперника со счётом 4:0
(серия T-019a…T-019e не давала выше 5 из 10). Не доказывает: (1) силу против сильного соперника —
нужен матч против обычного MCTS и против более высоких уровней; (2) устойчивость — четыре партии
мало, протокол D-017 требует десять; (3) достижение 5 кю — для этого нужен матч против заведомо
более сильной программы, которой в проекте пока нет.

**Почему лимит ходов, а не полная партия.** Партия сети против эвристики на 19×19 длится
200+ ходов; при 500 мс на ход это около минуты на партию у сети и секунды у соперника. Полный
протокол из десяти партий без лимита — это десятки минут на одно противостояние, поэтому серия
идёт частями, и каждая часть записывается отдельно.

**Последствия.** Следующий шаг — матч против обычного MCTS (уровень `Kyu10`, секунда на ход)
и расширение до десяти партий; после этого замер можно сравнивать с таблицей версий D-021.
Отдельно осталось подключить сеть к уровням в приложении: библиотека интерфейса не знает
про ONNX (порт `IPositionEvaluator` объявлен в `AI`, реализация — в `AI.Onnx`), поэтому
оценщик должен передавать голове приложение — это работа следующего шага.


## D-039. Специализированные нейросетевые модели по размеру доски

**Дата:** 2026-09-27
**Статус:** принято

**Контекст.** D-038 запретил использование нейросети KataGo (`b28c512nbt`) на доске 9×9 из-за неадекватных оценок. Однако KataGo распространяет специализированные модели, дообученные для конкретных размеров. В частности, релиз `v1.13.2-kata9x9` содержит модель `kata9x9-b18c384nbt-20231025.bin.gz`, которая на 9×9 до **200 Elo сильнее** основной модели.

**Решение.**
1. Ввести **профили моделей** — соответствие размера доски и файла ONNX.
2. Для 13×13 и 19×19 использовать основную модель `kata1-b28c512nbt-adam-s11165M-d5387M.uint8.onnx`.
3. Для 9×9 использовать специализированную модель `kata9x9-finetuned.uint8.onnx` (источник: katagotraining.org/extra_networks).
4. Если специализированная модель для размера не найдена — нейросеть **не используется**, уровень откатывается до MCTS.
5. `OnnxEvaluator` получает метод `LoadModelForBoardSize(int boardSize, string modelsDirectory)`.
6. `AiFactory` вызывает `evaluator.LoadModelForBoardSize(boardSize, modelsDirectory)` перед созданием уровня с нейросетью.

**Почему.**
KataGo — единая архитектура, но качество игры зависит от обучающего распределения. Специализированные модели решают проблему без изменения архитектуры приложения.

### Реализовано (T-035)

- `ModelProfile` и `ModelProfiles` в слое `AI.Onnx`.
- `IPositionEvaluator.LoadModelForBoardSize`.
- `AiFactory.Create` с параметром `modelsDirectory`.
- `LevelChooser` фильтрует уровни по наличию модели для размера.
- Голова `App.Desktop` передаёт каталог моделей.

### Модель для 9×9

- **Источник:** https://katagotraining.org/extra_networks/ (Small Board Networks)
- **Файл:** `kata9x9-b18c384nbt-20231025.bin.gz`
- **Целевое имя:** `kata9x9-finetuned.uint8.onnx`
- **Конвертация:** требует сборки KataGo с ONNX/TensorRT-бэкендом или внешнего конвертера.
- **Ограничение:** только для досок 7×7–11×11.

## D-040. Как получаем ONNX для 9×9: сборка KataGo с ONNX-бэкендом, иначе свой разбор `.bin.gz`

**Дата:** 2026-09-27
**Статус:** принято (задача T-036)

**Контекст.** Профиль `Finetuned9x9` ждёт файл `models/kata9x9-finetuned.uint8.onnx`, но модель
для 9×9 выложена только в нативном формате KataGo (`.bin.gz`, 93,3 МБ). Проверено в прошлом шаге:
команды `dumponnx` в опубликованной сборке Eigen(CPU) нет, а пайплайн `kaya-go/katago-onnx`
принимает PyTorch-чекпоинт `model.ckpt`, которого для этой модели публично нет.

**Решение.** Два пути по убыванию предпочтения:

1. **Собрать KataGo с `USE_ONNX_BACKEND=ON`** и выполнить `katago dumponnx -model … -out …`.
   Экспорт делает сам движок тем же кодом, которым его пользуется ONNX-бэкенд
   (`cpp/neuralnet/onnxmodelbuilder.cpp`), поэтому контракт тензоров совпадёт с уже подключённой
   моделью. Требуется MSVC + CMake + ONNX Runtime (dev).
2. **Свой разбор `.bin.gz`** (запасной путь): формат описан в исходниках KataGo
   (`cpp/neuralnet/modelversion.cpp`, `neuralnet.cpp`), из него собирается ONNX-граф с теми же
   входами и выходами, что у основной модели (`bin_input`, `global_input`, `policy`, `value`).

**Проверка результата — обязательна, независимо от пути.** Мало получить файл: нужно убедиться,
что он даёт осмысленную игру на 9×9 (первый ход в углу, вменяемая оценка) и что `OnnxEvaluator`
его принимает. Иначе «конвертация прошла» ничего не значит — как раз это и показал случай
с основной моделью на 9×9 (D-034), где формат был верный, а оценка бессмысленная.

**Чего не делаем.** Не подменяем специализированную модель основной и не переименовываем файлы
«чтобы профиль заработал»: 9×9 у основной сети играет неправдоподобно, и подмена вернула бы
именно ту проблему, из-за которой модель для 9×9 и понадобилась.


**Итог приоритета 1 (сборка KataGo с ONNX-бэкендом) — не выполнен за отведённый раунд.**

Что получилось: MSVC 19.51 (VS 18 Community) и Ninja работают, ONNX Runtime 1.20.1 для Windows x64
скачан и распакован (`tools/onnxruntime-win-x64-1.20.1`, есть `lib/onnxruntime.lib`), исходники
KataGo склонированы в `tools/KataGo-src`, CMake доходит до проверки зависимостей.

Что помешало:
1. первая попытка упала на моей ошибке с путём: `tools/katago` (скачанные бинарники) и `tools/KataGo`
   (исходники) на Windows — один и тот же каталог; исправлено именем `tools/KataGo-src`;
2. CMake требует **Eigen3** (`-DEIGEN3_INCLUDE_DIRS`); попытка скачать Eigen внутри `.cmd`
   завершилась кодом 9009 (команда не найдена в этом окружении), поэтому конфигурация снова упала;
   сборка до `katago.exe` не дошла.

По тайм-боксу приоритет 1 закрыт как неудачный, переходим к приоритету 2 — своему разбору
`.bin.gz` по `cpp/neuralnet/modelversion.cpp`. Скачанные исходники KataGo, ONNX Runtime и
сборка остаются в `tools/` (в git не попадают) и могут пригодиться как справочник по формату.


**Приоритет 2: разбор `.bin.gz` — критерии приёмки (согласованы) и первые данные.**

Критерий приёмки — не «число в узком диапазоне», а поведение кривой:

1. **Монотонность по коми**: пустая доска 9×9 при коми 0, 5,5, 7,5, 10, 15 — оценка за чёрных
   падает монотонно. Плоская кривая означает, что `global_input` не читается или веса не те.
2. **Совпадение с эталоном**: оценка специализированной модели должна совпадать с эталонным
   KataGo на том же файле в пределах 5 п.п. по всей кривой. Абсолютное значение при коми 5,5
   не нормируется: на 9×9 при коми 5,5 у чёрных преимущество, и модель показывает 77 %;
   эталон на том же файле даёт 81,6 %, то есть это мнение модели, а не дефект разбора.
3. **Контроль контракта**: сравнение с основной моделью применимо только к тем размерам, которые
   профиль ей и отдаёт (13×13 и 19×19). На 9×9-модели через наш API его провести нельзя: профили
   не пускают её на 13×13 — и это правильное поведение, а не отсутствие проверки.
4. **Первый ход** на пустой 9×9 при коми 5,5 — 3-4 или 3-3, не центр и не край.

Дополнительно фиксируются: число прочитанных тензоров против ожидаемого, совпадение
сигнатур (имя + форма) первых слоёв с основной моделью, непустые смещения, порядок тензоров.

**Что уже известно о файле** (снято скриптом `tools/read-bin-gz.py`):

- текстовая часть — 112 байт, 18 строк; двоичная — 105 532 426 байт, то есть **26 383 106 чисел
  float32**;
- заголовок: имя `kata9x9-b18c384nbt-s6603587840-d252232394`, версия модели `12`,
  число пространственных признаков `22`, размер обучения `19`, далее `trunk` и архитектура:
  блоков `18`, каналов `384`, головы `192 128 64 64`;
- первый тензор: `model.conv_spatial` с размерами `3 3 22 384 1 1` (ядро 3×3, вход 22 плоскости,
  выход 384 канала, дилатация 1×1) — совпадает с раскладкой признаков, которую мы уже кодируем;
- 22 пространственных признака подтверждают, что модель ждёт ту же раскладку, что и основная.

**Важное уточнение формата.** Описание *одного* тензора уместилось в текстовую часть до `@BIN@`;
значит остальные дескрипторы идут вперемешку с бинарными данными. Правило чередования нужно
прочитать в `cpp/neuralnet/modelversion.cpp` (исходники лежат в `tools/KataGo-src`) — от этого
зависит парсер, и угадывать здесь нельзя: ошибка порядка даст «формат верный, числа не те».


**Итог приоритета 2: модель сконвертирована и проверена (T-036).**

Файлы (в git не коммитятся, `models/*.onnx` в `.gitignore`): `models/kata9x9-finetuned.uint8.onnx`
(25,6 МБ) и `models/kata9x9-finetuned.onnx` (fp32, 100,6 МБ). Имя совпадает с
`ModelProfiles.Finetuned9x9`, поэтому профиль находит файл без правок кода.

Как получено: `dumponnx` в опубликованных сборках KataGo нет (приоритет 1 закрыт провалом),
поэтому написан свой разбор нативного формата по `cpp/neuralnet/desc.cpp` — веса чередуются
с текстовыми дескрипторами (имя, размеры, `@BIN@`, float32), затем граф собран на PyTorch и
экспортирован `torch.onnx.export` с динамическими осями и квантизован в uint8
(`quantize_dynamic`). Скрипты в `tools/`: `parse-bin-gz.py`, `build-onnx.py`,
`validate-model.py`, `check-model.py`.

**Проверка, выполненная мной независимо** (свой зонд на `OnnxEvaluator`, пустая 9×9, ход чёрных):

| Коми | Оценка за чёрных |
|---|---|
| 0 | 99,48 % |
| 5,5 | **77,00 %** |
| 7,5 | 5,62 % |
| 10 | 0,72 % |
| 15 | 0,03 % |

Кривая монотонно падает. Лучшие ходы при 5,5: D6 25,4 %, D4 24,0 %, F4 19,7 %, F6 18,0 %,
E5 4,1 % — это точки 3-4 и 4-4 в углу, центр (E5) почти не рассматривается. Мои числа
совпали с отчётом исполнителя (77,4 % и 4,50 %) в пределах 1,1 п.п., то есть сторона .NET
и Python-прогон согласованы.

**Критерий «50–70 % при коми 5,5» по букве не выполнен: 77 %.** Исполнитель прогнал тот же
`.bin.gz` самим движком KataGo (сборка Eigen, `kata-raw-nn`) и получил 81,61 % при 5,5
с совпадением по всей кривой в пределах 4,4 п.п. Это означает, что высокая оценка — мнение
самой модели, а не артефакт разбора. **Я эту эталонную проверку не повторял** — привожу её как
аргумент исполнителя, а не как свой результат.

**Критерий «13×13 при 7,5 — расхождение с основной моделью 5–10 п.п.» неприменим по конструкции.**
Первая моя попытка его выполнить оказалась ошибочной: я загрузил модель для 13×13 через тот же
оценщик и получил 15,19 % против 15,19 % — потому что профиль для 13×13 отдаёт **основную**
модель, и я сравнил её саму с собой. Заставить девятку считать 13×13 через наш API нельзя: ровно
это и запрещают профили (`Finetuned9x9` — 7…11, 13×13 берёт `Main19x19`). То есть контроль
в таком виде проверить нечем; исполнитель обошёл это в Python и получил 1,69 % против 15,52 %.

**Что это значит для приёмки.** Разделение профилей работает: на 9×9 движок берёт
специализированную модель и её кривая монотонна, первый ход в углу; на 13×13 — основную.
Оценка 77 % при коми 5,5 выше ожидаемого диапазона, но подтверждается эталоном KataGo;
порог «не 87 %» из D-034 относился к основной модели на 9×9 и здесь не нарушен.

**Рекомендации исполнителя, которые стоит решить отдельно:**
1. критерий приёмки полезнее сформулировать как «монотонность + совпадение с эталонным KataGo
   в пределах 5 п.п.» — иначе его не проходит ни одна честная реализация;
2. профиль `Finetuned9x9` объявлен как 7…11, а модель обучалась под 9×9 — либо замерить её
   на 7×7 и 11×11, либо сузить профиль до 9. В интерфейсе размеры только 9, 13 и 19, поэтому
   практического риска нет, но запись в профиле сейчас шире, чем проверено.

## D-041. Замеры на больших досках: 13×13 годится с основной моделью, бюджеты масштабировать не нужно

**Дата:** 2026-09-28
**Статус:** принято (замеры серии T-036/T-UI)

**Контекст.** После подключения специализированной модели 9×9 и появления лестницы нейросетевых
уровней (1 кю · 600 мс, 1 дан · 1500 мс, 5 дан · 4000 мс) нужно было ответить на три вопроса:
годится ли основная модель для 13×13 (турнирная доска пользователя), различает ли замер силу
на больших досках и не попадает ли минимальный бюджет сети в вырожденный режим. Отдельный
замер на 9×9 до этого дал отрицательный результат: при 2–5 итерациях поиска партии вырождены,
исход решает цвет.

**Что измерено (13×13, 4 партии, чередование цветов, лимит 200 ходов, зерно 20260926+n).**
- Калибровка: 140–160 мс на оценку модели, 26,5–28,2 мс на playout.
- Сеть 5 итераций против `Kyu20`, коми 5.5 — **4:0** (148:16,5 / 126,5:16 / 121:26,5 / 147,5:14).
- Сеть 2 итерации против `Kyu20`, коми 7.0 — **4:0** (126:32 / 135:19 / 135:20 / 136:19).
- В обоих матчах испытуемый выигрывал и чёрными, и белыми: исход цветом не определяется.

**Выводы.**
1. **Основная модель для 13×13 годится.** Эвристику 20 кю она громит и при пяти, и при двух
   итерациях; специализированная модель для 13×13 не нужна.
2. **Масштабировать бюджеты сети по размеру доски не нужно** — это была моя гипотеза, и замеры её
   не подтвердили. Слабейший бюджет (600 мс ≈ 2–4 оценки) на 13×13 уверенно сильнее 20 кю.
   Вырождение партий вызвано слабостью соперника, а не деградацией сети.
3. **Лестницу силы на больших досках обещать нельзя**: матчи «2 против 5 итераций» и
   «5 против 15» не сыграны (≈30 минут тихой машины), а против эвристики разницу бюджетов
   измерить невозможно — партии вырождены, у проигравшего остаётся 10–20 % камней.
4. **19×19 не измерялся**: один матч «5 итераций против MCTS 50 playout'ов» стоит ≈41 минуту.

**О методе, что важно на будущее.** Время одной оценки сильно зависит от загрузки машины: при
параллельной работе других задач замер показал 1007–1470 мс вместо 140–160, то есть до десяти раз
хуже. Поэтому бюджеты задаются в итерациях, а не во времени — тогда исходы и счёт от загрузки не
зависят, а числа времени считаются нижней оценкой. Вырождение партий (доля камней проигравшего
10–20 %) фиксируется как признак: такие партии годятся для вывода «сильнее вот этого», но не для
сравнения близких сил.

**Что осталось измерить.** Матчи сети с разными бюджетами на 13×13 (≈30 минут) и любой матч
на 19×19; результаты замеров на 9×9 при честном коми 7.0 (идут отдельным исполнителем).

## D-042. Партиями лестницу силы измерить нельзя: вырождение подтверждено, метод заменён

**Дата:** 2026-09-28
**Статус:** принято (замеры серии T-UI/T-036)

**Контекст.** Нужно было проверить, различает ли силу лестница нейросетевых бюджетов
(1 кю · 600 мс, 1 дан · 1500 мс, 5 дан · 4000 мс). Первый подход — матчи «сеть против сети»
на партиях с лимитом ходов — дал отрицательный результат, и его пришлось проверить на втором коми.

**Что измерено.** 9×9, лимит 150 ходов, 4 партии, чередование цветов:

| Коми | Счёт по площади | Камней в конце | Доля белых |
|---|---|---|---|
| 5.5 | Чёрные 81 : 5,5 (все четыре партии одинаково) | 73–74ч / **0б** | 0 % |
| 7.0 | Чёрные 74 : 10 и 67 : 16 | 59ч/3б и 58ч/9б | 4,8 % и 13,4 % |

Коми 7.0 сняло крайность (белые перестают исчезать полностью), но **вырождение осталось: победителя
определяет цвет, а не бюджет**. Тайминг на 9×9: 61,2 мс на оценку модели, 314 playout'ов/с у обычного
MCTS — то есть 33 итерации это ≈2 с на ход, 132 итерации ≈8 с.

**Вывод.** Постановка «сеть против сети, пустая доска, лимит ходов» не измеряет силу: при 8–33
итерациях нет ни playout'ов, ни глубины, поэтому защита от атари не считается, а сторона, которая
проигрывает по оценке, разваливается — и лимит ходов это вознаграждает. Дальнейшие матчи в такой
постановке бессмысленны, и полная серия (≈1,5 часа) не запускалась.

**Новый метод.** Сила лестницы измеряется тем, что не зависит от цвета:
1. **цумэго** — доля решённых позиций с известным ответом на каждом бюджете;
2. **точность оценки** — расхождение оценки победы с фактическим исходом партии на фиксированном
   наборе позиций;
3. **парные партии** — одна начальная позиция, цвета меняются, результат считается по паре, а не
   по отдельной партии (цвет сокращается), и только на 13×13, где партии осмысленнее.

**Что это меняет для продукта.** Названия уровней сети («1 кю», «1 дан», «5 дан») остаются
**номинальными**: доказано, что сеть уверенно сильнее эвристики 20 кю на 9×9 и 13×13 при любом
из проверенных бюджетов и сильнее обычного MCTS на 19×19 (D-037), но что ступени лестницы
различаются по силе — **не показано**. Обещать «5 дан» как проверенный ранг по-прежнему нельзя.

## D-043. Ступени нейросетевой лестницы не различаются измерением: ранги объявляются номинальными

**Дата:** 2026-09-28
**Статус:** принято (замеры серии T-UI)

**Контекст.** Партиями лестницу измерить не удалось: при коми 5.5 и 7.0 побеждал цвет, а не бюджет
(D-042). Тогда сила ступеней проверялась тремя методами, свободными от перекоса цвета.

**Что измерено.**
1. **Цумэго** (5 позиций, 9×9): решено **5 из 5 при всех бюджетах** — 8, 33 и 132 итерации.
   Набор насыщен: сеть берёт решающий ход уже на восьми итерациях, различать нечего.
2. **Точность оценки** (16 позиций одной партии): ошибка Brier **0,0464 / 0,0592 / 0,0699** для
   8 / 33 / 132 итераций — с ростом бюджета **не падает**. Лучший ход не изменился ни на одной позиции.
3. **Парные партии** 13×13 (сеть 5 против сети 15 итераций, 2 пары, цвета меняются): **ровно 50 %**,
   и во всех четырёх партиях победили **белые** независимо от бюджета.

**Противоречие, которое важно запомнить.** На пустой доске 13×13 при коми 5.5 модель считает
чёрных фаворитом (**61,7 %**), но все партии с поиском 5–15 итераций выиграли белые. Значит
в режиме лимита ходов исход определяется не статической оценкой модели, а чем-то другим — счётом
по площади на обрыве партии. Для замеров это приговор: **лимит ходов нельзя использовать как
условие сравнения сил** (подтверждает вывод, сделанный исполнителем по 9×9).

**Вывод.** Имеющимися средствами ступени лестницы (1 кю · 600 мс, 1 дан · 1500 мс, 5 дан · 4000 мс)
**не различаются**. Это не доказательство их равенства, а доказательство слепоты метода: политика
сети сильна уже сама по себе, а перекос цвета и лимит ходов перекрывают эффект бюджета.

**Продуктовое решение.** Ранги остаются **номинальными ориентирами**, а честная характеристика
уровня — движок и бюджет времени: «1 дан · нейросеть · 1.5 с/ход». Так и подписано в интерфейсе,
и это единственное, что мы вправе утверждать. Проверено замером: сеть уверенно сильнее эвристики
20 кю (9×9 и 13×13) и обычного MCTS на 19×19 (D-037); различие ступеней между собой — нет.

**Что различило бы ступени (если возвращаться к вопросу).**
1. Трудные позиции, где сеть ошибается при малом бюджете: 30–50 задач жизни и смерти, набранных
   анализом самой KataGo, вместо пяти простых.
2. Метрика потерь вместо совпадения хода: потеря вероятности победы относительно эталонного
   большого бюджета (eval-loss) чувствительнее бинарного «угадал ход».
3. Парные партии числом 20–30 при **сбалансированном коми** (по зонду для 13×13 это ≈6,2–6,5)
   и без лимита ходов либо с лимитом, при котором партия успевает завершиться двумя пасами.

## D-044. Разъяснение по 9×9: играть можно, модель не сломана, вырождение — свойство метода замера

**Дата:** 2026-09-28
**Статус:** принято (разъяснение к D-042/D-043)

**Вопрос, который возник у пользователя.** Если в замерах «всегда выигрывает цвет», значит ли это,
что на 9×9 играть нельзя или что модель сломана? И не потому ли это, что соперник был слабый (20 кю)?

**Ответ по пунктам.**

1. **Играть можно, и сеть на 9×9 сильна.** Матчи сети против эвристики 20 кю закончились **4:0**
   при любом проверенном бюджете, включая самый малый (2 итерации ≈ 0,12 с на ход). То есть даже
   слабейшая ступень сети уверенно обыгрывает эвристику — это измерено, а не предположено.
   Продуктовые уровни сети ещё выше: при 61,2 мс на оценку 600 мс ≈ 10 итераций, 1,5 с ≈ 25,
   4 с ≈ 65.

2. **Модель не сломана.** Проверено отдельно: скриптованная партия играется корректно (5ч/5б после
   10 ходов), селектор возвращает ходы своего цвета, политика осмысленна (лучший ход D6 с 97,5 %),
   кривая по коми монотонна, первый ход в углу.

3. **Вырождение — свойство метода замера, а не игры.** В матчах «сеть против сети» на 2–33 итерациях
   поиска нет ни playout'ов, ни глубины: сеть даёт только приоритеты и оценку листа. Сторона, которая
   по оценке проигрывает, не защищает атари и разваливается — и лимит ходов это вознаграждает.
   Поэтому побеждал цвет: при коми 5.5 модель считает чёрных фаворитом (77 %), и белые сыпались
   (0 камней к 150-му ходу); при коми 7.0 — 3–9 камней, лучше, но вырождение осталось.

4. **Слабый соперник (20 кю) — это другая, отдельная причина вырождения.** В матчах против него
   рассыпается **соперник** (10–20 % камней у проигравшего), и такие матчи годятся только для вывода
   «сильнее 20 кю», но не для сравнения бюджетов. В матчах «сеть против сети» 20 кю не участвовал
   вовсе — там вырождение вызвано малым бюджетом поиска.

**Следствие для продукта, которое стоит решить.** Коми 5.5 на 9×9 сама модель считает выгодным для
чёрных (77 %), то есть партия по нашим правилам не сбалансирована. По её же кривой равновесие лежит
около 6,5–7,0. Варианты: (а) поднять коми для 9×9 до 7,0 и получить честную игру; (б) оставить 5.5
как правило проекта и знать, что чёрные в выигрыше. Решение за пользователем, правка — одна строка
в `Komi.For9x9`, но менять правила игры без его слова нельзя.

## D-045. Сильные уровни — только с сетью: замер 13×13 подтвердил 11:0

**Дата:** 2026-09-28
**Статус:** принято (замеры серии T-UI)

**Контекст.** Уровни кю (MCTS со случайными playout'ами) на больших досках играют слабо: при 27 мс
на playout на 13×13 три секунды на ход дают около 112 мысленных партий, чего не хватает даже на то,
чтобы наказывать группы в атари. Нужно было проверить, действительно ли сеть сильнее сильнейшего
уровня без сети, — прежние матчи сравнивали её только с эвристикой 20 кю.

**Что измерено** (13×13, коми 5.5, лимит 200 ходов, 4 партии с чередованием цветов, бюджеты в итерациях;
калибровка 137–165 мс на оценку, 144–156 playout'ов/с):

| Матч | Счёт | Счёт по площади | Доля камней проигравшего |
|---|---|---|---|
| сеть 5 итераций против `Kyu5` (3 с/ход) | **4:0** | 133:31,5 / 150,5:9 / 127:21,5 / 129,5:28 | 8–21 % |
| сеть 5 итераций против `Kyu10` (1 с/ход) | **4:0** | 142:17,5 / 129,5:20 / 135:26,5 / 154,5:10 | 9–17 % |
| сеть 5 итераций против `Kyu8` (2 с/ход) | **3:0** (3 партии из 4, лимит времени) | 140:21,5 / 132,5:15 / 143:16,5 | 10–14 % |
| сеть 5 против сети 15 итераций | 2 из 3 | 93:63,5 / 93:62,5 / 93:63,5 | 39,8 % |
| сеть 2 против сети 5 итераций | 2 из 3 | 93:62,5 во всех трёх | 39,8 % |

**Выводы.**
1. **Сеть сильнее всех уровней без сети: 11 побед в 11 партиях**, и чёрными, и белыми, с запасом
   95–145 очков. Минимальный сетевой бюджет (5 итераций ≈ 0,7 с на ход) обыгрывает сильнейший
   MCTS-уровень проекта (`Kyu5`, 3 с на ход) — то есть на больших досках сильные уровни обязаны
   играть сетью, а не поиском по случайным доигрываниям.
2. **Лестницу сети партиями измерить нельзя и на 13×13.** Сетевые уровни детерминированы (без
   случайности), поэтому партии повторяются побайтово, а исход решает цвет: во всех шести партиях
   сети против сети победили чёрные при коми 5.5. «2 из 3» здесь означает «чёрные сильнее при этом
   коми», а не «бюджет больше — сильнее».
3. **Признак вырождения работает:** против уровней кю проигравший держит 8–21 % камней (рассыпается),
   в матчах сети против сети — 39,8 % (борьба ровнее, но решает цвет).

**Продуктовые следствия.** Уровни кю на 13×13 и 19×19 в нынешнем виде бесполезны — это подтверждено
числами и совпадает с жалобой пользователя «подставляется под съедение сразу». Отсюда правка,
которая уже в работе: тактический предохранитель (запрет самоатари, обязательный разбор атари
противника и своей группы) и перевод уровней 15/10/8/5 кю на сеть с малым бюджетом при наличии
модели для размера.

**Чего не сделано.** Матчи на 9×9 при коми 7.0 не запускались (серия вышла за лимит времени);
матчи лестницы сыграны по 3 партии из 4. Лимит 200 ходов не даёт партиям завершиться пасами, поэтому
для тонких сравнений нужен другой метод: случайные дебюты с разными зёрнами (снимает детерминированность),
гандикап для выравнивания цвета либо оценка качества решений на позициях с известным ответом.

## D-046. Тактический предохранитель: подстановки устранены, силу он не измеряет

**Дата:** 2026-09-28
**Статус:** принято (правка по жалобе пользователя на тактику)

**Контекст.** Пользователь: «все уровни кю очень тупые, новичок обыгрывает, движок подставляется
под съедение сразу и тактику не прорабатывает независимо от времени хода». Числа это подтверждали:
на 13×13 сеть выиграла у всех уровней без сети 11:0, а при 27 мс на playout три секунды дают ≈112
мысленных партий, чего не хватает даже на наказание групп в атари (D-045).

**Что сделано.** В слое `AI` появился `TacticalGuard`: ход, после которого своя группа получает одно
дамэ, отклоняется (исключения — ход снимает камни, группа уже в атари, или это единственный легальный
ход). Фильтр подключён в `MctsMoveSelector`, `HeuristicMoveSelector` и `AiFactory`.

**Найденный и исправленный дефект самого предохранителя (важнее самого фильтра).** Первая версия
проверяла ход через `Board.ApplyMove` на доске **с историей партии**, а `ApplyMove` дописывает позицию
в `PositionHistory` — проверка съедала суперко-историю, и партия рассыпалась. Исправлено: проверка
идёт по копии без истории (`WithoutHistory()`) плюс предварительная проверка легальности. Числа
«до и после»:

| Проверка | До | После |
|---|---|---|
| Kyu15, партия через `GameState` | 2 хода, 2 отклонены суперко | **120 ходов, 0 отклонённых** |
| Kyu20, партия через `GameState` | 6 ходов, 2 отклонены | **120 ходов, 0 отклонённых** |
| Kyu15, 23 позиции | **20 нелегальных ходов из 23** | 0 из 23 |
| Kyu10, 8 позиций | **8 нелегальных из 8** | 0 из 8 |

**Числа по тактике** (стенд `tools/guard-probe`, 23 позиции × 3 зерна = 69):
подстановки — Kyu25 6→0, Kyu20 6→0, Kyu15 22→0; Kyu30 (чистый случай) 4→4 — его намеренно
не защищаем. Цумэго 5/5 с предохранителем и без него (набор насыщен, силы не различает).
Семантика фильтра: 7 из 7 проверок «ок» (самоатари отклоняется; продление, захват, защита в атари
и пас разрешены; история партии не пополняется).

**Чего предохранитель не даёт.** Матч «до против после» прироста силы **не показал**: 9×9 Kyu15
3:7, 9×9 Kyu20 4:6, 13×13 Kyu15 3:1, 13×13 Kyu20 1:3 — победитель следует цвету, а не версии,
партии вырождены. Поэтому заявлять силу нельзя; заявлено другое и проверенное: **подстановки
и нелегальные ходы устранены**.

**Не сделано сознательно.** Усиление приоритетов захватов и спасения в самом поиске MCTS:
приоритеты уже есть в эвристическом селекторе через `AtariHeuristics`, а менять порядок обхода
дерева без замера силы — значит заявлять недоказанное. Нужен отдельный протокол, где цвет
не доминирует (случайные дебюты или гандикап).

## D-048. Подпись уровня называет движок, который действительно сядет играть

**Дата:** 2026-09-28
**Статус:** принято (правка интерфейса по жалобе «непонятно, кто играет»)

**Контекст.** После D-045 уровни кю играют сетью, когда для размера доски есть модель, и обычным
MCTS, когда модели нет. Подпись в списке уровней оставалась статической (`LevelChooser.Label`):
она показывала «MCTS без сети» уровню, который на 9×9 фактически играл сетью, и «нейросеть» уровню,
который без модели играет MCTS. Интерфейс обещал не тот движок.

**Решение.** Список уровней (`MainViewModel.LevelLabels`) собирает `LevelChooser.Describe` с размером
текущей доски и признаком наличия модели — та же подпись, что и в панели партии. Статический `Label`
остаётся там, где контекста доски нет (экран настроек). Бюджет в подписи — тот, которым поиск
действительно ограничен: у уровня кю с сетью это бюджет сети на ход, у остальных — бюджет уровня.

**Проверка.** `LevelChooserTests`: кю-уровень с моделью читается как «10 кю · нейросеть · N мс/ход»,
без модели — «10 кю · MCTS без сети · 3 с/ход»; `MainViewModelTests` сверяет каждую подпись списка
с `Describe` и её бюджет. Регрессия теста: прежняя проверка закрепляла статическую подпись
(«MCTS без сети»), то есть зелёный тест на неверное для 9×9 поведение.

## D-051. Коми следует за размером доски: размеры, подписи и правило — в одном месте

**Дата:** 2026-09-28
**Статус:** принято (фаза 11, срез 1b; исправление дефекта, найденного снимком окна)

**Что было не так.** На доске 9×9 панель показывала «Коми: 7.5». В настройках смена размера
доски перестраивала только список уровней и не трогала поле коми, поэтому вместе со сменой
размера уезжало значение от прежней доски: в файле настроек на этой машине лежала пара
`{"boardSize":9,…,"komi":7.5}` — доска 9×9 с коми от 19×19. По правилам для 9×9 коми 5,5
(`GO_RULES.md`, п. 10; D-049), значит счёт партии считался бы не по правилам.

**Причина глубже одного поля.** Список размеров доски и подписи были продублированы: в модели
представления (`Sizes`, `SizeLabels`, свой `Describe`) и в виде настроек (`Sizes` как `byte[]`
и `${size}×${size}`). Правило коми жило только в модели представления (`StartWith` через
`Komi.For`), поэтому вид настроек о нём не знал.

**Решение.** Новый сервис `GoEngine.App/Services/BoardSizes.cs` — одно место про размеры доски:
`All` (9, 13, 19), `Labels` («9×9», «13×13», «19×19», тот же экземпляр списка), `IndexOf`,
`At` (вне списка — размер сброса 9×9), `Label`, `KomiFor` (правило — `Komi.For`). Оба вида
пользуются им; публичный API модели представления не изменился. `SettingsView.OnSizeChanged`
теперь пересчитывает и список уровней, и коми по правилу новой доски. Порядок в `Initialize`
сохранён: сначала размер, потом коми из сохранённых настроек — правило срабатывает на смену
размера игроком, а не на открытие окна, иначе осознанно выставленное коми затиралось бы.

**Проверка.** `BoardSizesTests` — 15 тестов: состав и порядок размеров, подписи (и что список
не пересоздаётся), `IndexOf`/`At`/сброс вне диапазона, значения правила (9×9 и 13×13 — 5.5,
19×19 — 7.5) и две регрессии: «настройки 9×9 + 7.5 после смены доски дают 5.5» и «сохранённое
коми не затирается правилом при открытии настроек». Сборка `-warnaserror` — 0 предупреждений,
тесты приложения 97 из 97, режимы `--settings` и `--check` — код 0.

**Чего тесты не покрывают — и как это проверено.** Сам вид настроек (Avalonia) юнит-тестами
не покрыт, поэтому смену размера проверили в живом окне автоматизацией UI (UI Automation):
старт — доска 9×9 и коми 7.5 из старого файла настроек (сохранённое значение не затирается),
затем выбор 13×13 → 5.5, 19×19 → 7.5, 9×9 → 5.5. Файл настроек при этом не переписывается:
он сохраняется только по кнопке «Начать партию». Файл `%APPDATA%\GoEngine\settings.json` на этой
машине остаётся с парой «9×9 + 7.5» до первого согласия с настройками — исправление меняет
поведение при смене размера, а не правит чужой файл.

## D-052. Срез 2 рефакторинга: поиск, оценка и отбор ходов — три обязанности вместо одной

**Дата:** 2026-09-28
**Статус:** принято (фаза 11, срез 2); отклонение от плана среза описано ниже

**Что было.** `MctsMoveSelector` (393 строки) совмещал поиск по дереву, оценку позиции (доигрывания
либо сеть с PUCT и приоритетами политики) и знание о тактическом предохранителе. `TacticalGuard`
вызывался из трёх мест, а правило «безопасных ходов нет — играй любой» было продублировано трижды.

**Что стало.**

| Тип | Обязанность |
|---|---|
| `MctsSearch` | дерево и бюджет: время через `TimeProvider` либо число итераций |
| `IMctsEvaluation` + `PlayoutEvaluation` / `NeuralEvaluation` | чем оценивается узел: случайное доигрывание или сеть (PUCT, приоритеты, порядок разбора) |
| `IMoveFilter` + `TacticalMoveFilter` / `MoveFilters` | отбор ходов: правила предохранителя в одном месте |
| `MctsMoveSelector` (194 строки) | публичный вход: конструкторы, `Name`, `SelectMove`, `Search` |

**Отклонение от плана среза (принято).** Планировался декоратор `GuardedMoveSelector : IMoveSelector`.
Он не подходит по двум проверяемым причинам: (1) тесты жёстко фиксируют тип, который возвращает

этого не воспроизводит. Поэтому предохранитель стал портом отбора ходов (`IMoveFilter`), а не
декоратором; `MctsConfig.TacticalGuard` и `HeuristicMoveSelector(tacticalGuard:)` остались рабочими
и сводятся к одной строке `MoveFilters.Guarded(flag)`. Если понадобится именно декоратор, нужен шов
«пул кандидатов + выбор из пула» и правка type-pinned тестов — это отдельная работа.

**Как проверено, что поведение не изменилось (не на глаз).** Зонд `tools/golden-probe` (в индекс
не попадает) играет четыре партии по 24 хода через `GameState` (суперко и история внутри проверки)
при бюджетах в итерациях и фиксированном зерне: MCTS с предохранителем, MCTS без него, эвристика
(случайность 40 %) и MCTS с подставной сетью (PUCT, приоритеты, порядок разбора). Последовательности
сняты с кода до правок, а затем сверены **независимо**: тот же зонд прогнан в отдельной рабочей копии
на дорефакторном коммите `732a225` — совпадение посимвольное, и на текущем коде — тоже. Четыре
последовательности по 24 хода совпали во всех трёх прогонах.

**Тесты.** +18: `GoldenMoveSequenceTests` (те самые четыре партии как ожидаемые данные),
`MoveFilterTests` (самоатари отклоняется; захват, защита в атари, продление и пас разрешены;

## D-053. Срез 3 рефакторинга: сессия модели, разбор выходов и оценщик — три обязанности вместо одной

**Дата:** 2026-09-28
**Статус:** принято (фаза 11, срез 3); два решения внутри требуют внимания

**Что было.** `OnnxEvaluator` (303 строки) держал всё: жизненный цикл сессии ONNX Runtime, выбор
профиля модели по размеру доски, имена входов и выходов, вывод и превращение сырых тензоров
в `PositionEvaluation`. Математику нельзя было проверить без модели, а загрузку — без вывода.

**Что стало.** `ModelSession` (жизненный цикл `InferenceSession`, имена входов/выходов, `Run` →
сырые логиты), `EvaluationReader` (проверки формы и softmax политики, без ONNX и без модели —
поэтому покрыт тестами), `OnnxModel` (публичные `OnnxTensorInfo`, `OnnxModelInfo`, `OnnxEvaluation`
переехали дословно). `OnnxEvaluator` 303 → 141 строка — тонкая точка входа с тем же публичным API.
`KataGoFeatures` и `ModelProfiles` не тронуты (ноль строк).

**Решение 1: тесты видят внутренние типы.** В `GoEngine.AI.Onnx.csproj` добавлен
`<InternalsVisibleTo Include="GoEngine.Tests" />`. Это единственный способ проверить сессию и разбор,
не расширяя публичный API проекта; расширять API ради тестов хуже, чем открыть внутренности одной
сборке тестов. Средство новое для проекта — записано здесь, чтобы не выглядело случайностью.

**Решение 2: проверки формы тензоров вместо молчаливых нулей.** Политика короче «площадь + 1»
или площадь ≤ 0 теперь дают `DomainException` с русским сообщением; раньше возвращались нули.
Для поставляемых моделей это недостижимо, и это доказано не рассуждением, а числами: 24 оценки
совпали побайтово. Семантика `DllNotFoundException` сохранена точно (ловится только в `Load`).

(`policyBits`, `valueBits`, `winBits`, `sumBits`) для 24 оценок: 9×9 на дообученной модели,

расхождение 0 бит. Я проверил это независимо: тот же зонд прогнан в отдельной рабочей копии на
дорефакторном коммите `dc52cc9` — тот же SHA-256. Попутно подтвердилось строение голов: у модели
9×9 политика компактная (82 значения: 81 точка и пас), у основной — 362.

**Тесты.** +17 (ничего не удалено): `EvaluationReaderTests` (9 — сумма вероятностей, порядок,

## D-054. Конец партии, территория и отмена хода — три жалобы после живой игры

**Дата:** 2026-09-28
**Статус:** принято (правки по замечаниям пользователя после партий на 9×9 и 13×13)

**Жалобы, дословно.** «Сказал по кнопке несколько раз пас — противник доел мои камни, а потом начал
ходить и стал поедать свои же очки не останавливаясь»; «не хватает обозначения территории чёрных
и белых на досках»; «когда партия с моей стороны закончилась, а противник продолжал ходить — я нажал
на кнопку отменить — игра сломалась».

**1. Соперник останавливается.** Причина: селекторы отдавали ход всегда, когда есть формально
легальные ходы, а предохранитель при «безопасных ходов не осталось» разрешал любой ход вместо паса,
поэтому заполнение собственной территории ничем не отличалось от полезного хода. Правило вынесено
в `EndgamePolicy` и подключено к `MctsMoveSelector` и `HeuristicMoveSelector`: (1) ход, который
снимает камни, спасает свою группу из атари или прижимает чужую до одного дамэ, играется всегда;
(2) ход внутрь своей территории, который ничего не даёт, не играется; (3) если соперник только что
пропустил ход, играются лишь ходы, увеличивающие очки ходящего; (4) если ходов не осталось — пас,
и партия завершается двумя пасами. «Своя территория» берётся из `Scorer.Ownership`, очки — из
`Scorer.Calculate`, второго подсчёта нет.

**2. Территория показана.** Подсчёт в `Core` был верен: сверка с `GO_RULES.md` (пункты 69, 70, 72, 73)
расхождений не нашла. Добавлен аддитивный `Scorer.Breakdown` (камни, территория и нейтральные точки
по цветам), и `Calculate` берёт очки оттуда же, поэтому панель и счёт разойтись не могут. На доске
рисуются знаки только на пустых точках: чёрный квадрат — территория чёрных, белый квадрат с обводкой —
белых, серый крест — нейтральные. Показываются по переключателю «Территория» и автоматически
в завершённой партии; в панели — расшифровка «камни + территория, нейтрально, коми».

**3. Отмена перестала ломать партию.** Причина найдена воспроизведением: `MainViewModel.Undo`
отменял ход и затем откатывал ходы, пока очередь не вернётся игроку, но если вернуть её было нельзя
(в истории только ход соперника), цикл заканчивался на состоянии «ходит соперник», а ход соперника
никто не запускал — партия зависала, и щелчки игрока играли за соперника. Добавлены предпросмотр
в `GameState` (`CanUndoTo`/`CanRedoTo`), полный откат собственных отмен в `TryUndo`/`TryRedo`,
связь кнопок с `CanUndo`/`CanRedo` и страховка «хода-полухода» (если партия не приняла ход
селектора, соперник пасует).

**Проверка — не только тестами.** Тесты: 581 + 2 пропущенных в `GoEngine.Tests` (было 527),
112 в `GoEngine.App.Tests` (было 97), включая 27 тестов подсчёта территории и сценарий жалобы
через `GameState` (человек пасует — соперник пасует — партия завершена). Живая проверка
автоматизацией интерфейса: старт — отмена и возврат недоступны; после моего паса соперник сходил
(номер хода 2, отмена доступна); **после второго паса партия завершилась двумя пасами** (номер хода 4,
статус «Завершена двумя пасами»); панель показала «Площадь: чёрные 0 (камни 0, территория 0),
белые 81 (камни 1, территория 80), нейтрально 0 · коми 7.5 белым»; отмена после завершения вернула

## D-055. Коми от чужой доски исправляется при загрузке; формулировка территории уточнена

**Дата:** 2026-09-28
**Статус:** принято (следствие D-051 и замечания про территорию)

**Наследие дефекта D-051.** Дефект «смена размера доски не пересчитывала коми» успел записать
в файлы настроек пару «9×9 + коми 7.5» — значение, верное для 19×19. Пользователь видит такое
и в счёте партии. Решение: при загрузке настроек пара распознаётся и заменяется правилом для доски
(`AppSettings.RepairKomi`, вызов из `SettingsStore.Load`). Признак однозначный: для 9×9 и 13×13
коми 7,5 правилами не предусмотрено (`GO_RULES.md`, п. 10; D-049). Обратный случай (19×19 с коми 5,5)
не трогаем: 5,5 на большой доске — допустимый выбор игрока, и от наследия дефекта он неотличим.

обычным путём, когда игрок соглашается с настройками. Проверка — 9 тестов `KomiRepairTests`
(в том числе «осознанное 6,5 на 9×9 не трогаем» и «файл не изменён»).

**Неточность канона.** Пункт 71 `GO_RULES.md` был сформулирован так, что территории у края доски
не существовало бы вовсе («все пути до края проходят только через точки цвета C»), что противоречит
пунктам 69–70, позиции из п. 13.8 и общепринятым правилам: край доски границу области завершает
и является стеной для обеих сторон. Исполнитель канон не правил, а зафиксировал трактовку в доке
`Scorer` — правильно, потому что канон меняет владелец. Формулировка уточнена в `GO_RULES.md`:
точка окружена цветом `C`, если она пустая и вся граница её связной пустой области состоит только
из камней `C`; край доски границу завершает; если на границе есть камни обоих цветов — точки
нейтральны. Код при этом не менялся: `Scorer` уже считал по этой трактовке, и 27 тестов территории
(угол, край, сэки, все три доски) это подтверждают. Внешняя опора: определение площади в правилах
(«area состоит из занятых и окружённых точек», <https://en.wikipedia.org/wiki/Rules_of_go>).

## D-056. Уровни кю играют поиском: лестница итераций вместо эвристик без поиска

**Дата:** 2026-09-28
**Статус:** принято (замечание пользователя: «30, 25, 20 кю очень слабые, нужна MCTS модель;
15 кю классная с нейросетью, а 20 кю слишком тупая на её фоне»)

**Что было.** 30 кю — случайные ходы, 25 и 20 кю — эвристики без поиска, 15 кю — MCTS с сетью
на 300 мс. Разрыв между 20 и 15 кю был виден игроку сразу.

**Что стало.** Вся лестница кю играет поиском, бюджет задаётся **в итерациях** (одна итерация —
один вызов сети), а не во времени, поэтому сила ступени не зависит от скорости машины, а время хода
подстраивается под доску. Новый тип `NeuralBudget` задаёт итерации отдельно для 9×9, 13×13 и 19×19.

| Уровень | Движок с сетью (9×9/13×13/19×19) | Без сети | Случайность |
|---|---|---|---|
| 30 кю | MCTS, 1/1/1 итерация | 2 playout'а | 60 % |
| 25 кю | MCTS, 2/2/2 | 8 playout'ов | 35 % |
| 20 кю | MCTS, 3/3/3 | 24 playout'а | 15 % |
| 15 кю | MCTS, 5/4/3 | 48 playout'ов | 8 % |
| 10 / 8 / 5 кю | MCTS, 9/7/5, 14/11/8, 20/16/12 | время как было (1/2/3 с) | 8/3/0 % |
| 1 кю, 1 и 5 дан | сеть, 26/21/15, 34/27/20, 44/35/25 | — | 0 % |

Слабость уровня теперь выражается числом итераций и случайностью, а не отсутствием поиска: случайный
ход по-прежнему проходит через тактический предохранитель (D-046) и правила конца партии (D-054),
поэтому уровень ошибается, но не подставляет группы и не доедает свою территорию.

**Числа (9×9, коми 5.5, 10 партий на пару, цвета чередуются, зёрна 20260926+n, стенд `tools/ladder-probe`).**

| Пара | С сетью | Без сети |
|---|---|---|
| 20 кю против 25 кю | 9:1 | 7:3 |
| 25 кю против 30 кю | 10:0 | 8:2 |

Победы по цвету близки к равным (6:4, 5:5, 4:6, 5:5) — цвет исход не решает. Детерминизм проверен:
повтор партии с тем же зерном даёт те же 145 ходов и тот же счёт. Партии по-прежнему вырождаются
(проигравший сохраняет 9–30 % камней), поэтому вывод «насколько сильнее» не делается: D-047 в силе,
ранги остаются номинальными.

**Ломающее изменение публичного API, принятое сознательно.** `DifficultyLevel.NeuralBudget` был
`TimeSpan?`, стал `NeuralBudget?` (итерации на три размера доски). Держать рядом мёртвое свойство
со временем не стали: у проекта один потребитель — приложение, внешних пользователей API нет, а
итерации дают детерминизм замеров. Если понадобится совместимость, время возвращается отдельным
свойством аддитивно.

**Тесты.** 581 → 591 (+2 пропущенных) в `GoEngine.Tests`, 121 в `GoEngine.App.Tests`. Матч
«20 кю против 30 кю» в тестах сокращён со 100 до 20 партий: уровни теперь ищут, и полная серия стоила
~9 минут — полная серия живёт в стенде. Проверки эвристик (спасение группы в атари, захват, угол)
переведены на прямой `HeuristicMoveSelector` с той же случайностью, покрытие сохранено; добавлен
`LevelLadderTests` (монотонность бюджетов, разведение 30 и 25 кю случайностью на 19×19).

**Честные оговорки.** Метрика подстановок на 10 позициях дала 0 из 10 у всех вариантов, включая
прежнюю эвристику и случайные ходы: она насыщена и усиление **не** доказывает. Усиление заявлено
по двум фактам: все уровни играют поиском, и матчи упорядочились 9:1 и 10:0 (прежде лестница была
неразличима). Силу ступеней внешним соперником по-прежнему не мерили.

## D-058. Linux-сборка была нерабочей: нативная Skia 2.88 при управляемой 3.116

**Дата:** 2026-09-28
**Статус:** принято (дефект найден при разборе красного CI, исправлен)

**Как нашли.** Linux-джоба CI упала на четырёх новых тестах отрисовки территории: «версия нативной
`libSkiaSharp` (88.1) несовместима с этой версией SkiaSharp, поддерживаются версии из диапазона
[116.0, 117.0)». Локальный гейт на Windows был зелёным, поэтому дело было не в тестах.

**Что оказалось на самом деле.** Я скачал **опубликованные релизные артефакты** и проверил нативную
библиотеку внутри каждого:

| Платформа | Файл | Версия нативной Skia |
|---|---|---|
| Windows | `libSkiaSharp.dll` | 116 (работает, приложение запускали) |
| macOS arm64 | `libSkiaSharp.dylib` | 116 |
| Android | `lib/<abi>/libSkiaSharp.so` | 116 |
| **Linux x64** | `libSkiaSharp.so` | **88.1** |

То есть не тесты, а **сама сборка для Linux**: приложение для Linux в текущем релизе не смогло бы
инициализировать Skia и не показало бы окно. Причина видна в разрешении пакетов
(`obj/project.assets.json`): `SkiaSharp.NativeAssets.Linux` разрешался в **2.88.8** (транзитивно,
через `Avalonia.Skia` 11.2.1), тогда как управляемая `SkiaSharp` — 3.116.1; нативные библиотеки для
Windows и macOS приходят из самой `SkiaSharp` 3.116.1 и потому были верными.

**Исправление.** `SkiaSharp.NativeAssets.Linux` 3.116.1 объявлен явно: версия в
`src/Directory.Packages.props`, ссылка — в голове `GoEngine.App.Desktop` (там же, где `SkiaSharp`),
пакет упомянут в списке стека `PROJECT.md`. Заодно вернулась работоспособность четырёх тестов
отрисовки территории на Linux: они и были той проверкой, которая поймала дефект.

**Проверка.** Локальная кросс-публикация `dotnet publish -r linux-x64` теперь кладёт
`libSkiaSharp.so` размером 8,6 МБ со строкой версии **116** (до правки — библиотека 2.88 из архива
релиза). Окончательная проверка — Linux-джоба CI и новый релизный архив: в нём должна лежать
библиотека 116, а тесты отрисовки на Linux должны стать зелёными.

**Чему это учит (записано в блокеры).** Сборка и `--smoke` на раннере не проверяют, что приложение
на этой платформе вообще может отрисоваться: несовпадение нативных зависимостей видно только при
реальном использовании графики. Тесты отрисовки на каждой платформе — самая дешёвая страховка.

## D-059. Срез 4 рефакторинга: правила хода и снятие групп вынесены из доски

**Дата:** 2026-09-28
**Статус:** принято (фаза 11, срез 4; поведение и публичный API не менялись)

**Что было.** `Board` (367 строк) держала в одном типе и позицию, и правила постановки камня

|---|---|

**Как доказано, что правила не изменились.** Три опоры, а не «тесты зелёные»:
1. Все 591 тест `GoEngine.Tests` (+2 пропущенных) и 171 тест приложения проходят без правок —

2. «Золотые» партии `GoldenMoveSequenceTests` играются через `GameState` (суперко и история внутри)
   и совпадают ход в ход.
3. Независимый зонд `tools/core-check` (в индекс не попадает) играет фиксированный сценарий из
   40 шагов — обычные ходы, пасы, попытки хода в занятую точку и после завершения партии — и печатает

   (коммит `2031807` в отдельной рабочей копии) и на коде после среза совпал **побайтово**:
   SHA-256 `92230FA1D8B8BAE4F6FA6506753B2451CB55EA488E9C3CCCB10315D8ECD0F999`, 43 строки.

**Зачем это нужно.** `Board` была самым большим типом `Core` и единственным, где правила игры
перемешаны с хранением позиции: чтобы проверить правило, приходилось читать весь тип. Теперь правило
суперко и проверка самоубийства читаются отдельно от массива камней, а доска занимается только
позицией — это и есть цель среза при неизменном поведении.

## D-061. Второй режим — задачи на жизнь и смерть: отдельный проект и свой контент

**Дата:** 2026-09-28
**Статус:** принято (новая задача пользователя)

**Что просил пользователь.** Добавить, как на `goproblems.ru`, интерактивные задачи на выживание
(цумэго). Два режима: сама партия (как сейчас) и отдельно задачи. Логику игры, тесты и линии
поставки не ломать, логику не смешивать, обеспечить работу на всех платформах. Приёмка: агент сам
запускает игру, решает задачу и следит за правильностью результата — и при прохождении, и при
неправильном ходе.

**Решение 1: отдельный проект.** Логика задач не кладётся ни в `Core`, ни в `AI`, ни в `App`:
создаётся проект `GoEngine.Problems` (ссылается на `Core` и `AI`), приложение ссылается на него.

по построению, а не по договорённости. Проверка цели использует существующие `EyeDetector`
(`AI`) и правила `Core`, второго движка не появляется.

**Решение 2: контент только свой.** Задачи с `goproblems.ru` и других сайтов **не копируются** —
это чужие авторские материалы. Сайт используется как образец формата и подачи (позиция, чей ход,
цель, подсказка, разбор), а позиции мы придумываем сами и проверяем движком.

**Решение 3: корректность доказывается движком, а не обещанием.** У каждой задачи есть дерево
решения: в каждом узле — множество принимаемых ходов, у каждого — продолжение (ответы соперника),
в листьях цель достигнута. Тест обходит **все** ветви: каждый принимаемый ход легален по правилам,
в каждом листе цель действительно выполнена — для цели «убить» целевой группы на доске нет, для цели
«обеспечить жизнь» у группы два настоящих глаза. Задача, которую движок не подтверждает, в набор
не попадает.

**Решение 4: режимы не смешиваются в интерфейсе.** Переключатель режимов («Партия» / «Задачи»)
и отдельный вид задачи со своей моделью представления; вид партии не переписывается. Раскладка
задачи адаптивная — та же логика узкого экрана, что у доски партии (`BoardLayoutRules`), чтобы
режим работал и на телефоне.

**Границы первой очереди.** Домен, библиотека задач (не меньше 12, разные типы: три точки, ханэ,
подкладочный камень, снэпбэк, ложный глаз, два глаза, угловой захват), сессия решения с вердиктами
и тесты. Интерфейс, Android и приёмка — следующие заходы.

**Приёмка (определение готовности от пользователя).** Я запускаю приложение, решаю задачу правильно
до вердикта «решена», затем решаю её же неправильно и вижу внятный отказ с правильным ходом.
Оба исхода подтверждаются снимками экрана и тестами.

## D-062. Задачи: правило согласованности, горизонт 3 и новые типы

**Дата:** 2026-09-28
**Статус:** принято (заход 1c: части A и B)

**Что просил пользователь.** Завершить второй режим: контент задач должен подчиняться одному
обязательному правилу — принимаемый набор в каждом узле равен множеству выигрывающих ходов
на заявленном горизонте. Если другой ход тоже убивает группу, а дерево его не принимает,
приложение скажет игроку «неверно» за правильный ход: это ложный отказ, и он недопустим.
Плюс — недостающие типы задач (подкладной камень, ложный глаз, снэпбэк, многоходовая жизнь)
и видимое из API число принимаемых первых ходов.

**Решение 1: правило согласованности.** В узле решающего принимаются **все** ходы, выигрывающие
на остатке заявленного горизонта, и только они. В узле защищающегося выигрышных ходов нет; дерево
хранит самый упорный ответ (при равенстве — ближайший к целевой группе, затем канонический порядок
обхода доски). Дерево генерируется перебором, руками не пишется. Правило и его следствия —
`PROBLEMS.md`, разделы о правиле согласованности и о горизонте; проверка — `ProblemConsistencyTests` (расхождение роняет тест).

**Решение 2: подсказка.** Подсказка — самый быстрый выигрывающий ход; при равенстве — канонический
по порядку обхода доски (`Board.AllPoints`: строка за строкой, слева направо). Первый принимаемый
ход корня — он же `Problem.Hint`.

**Решение 3: горизонт у задач захвата — 3 полухода.** Шесть задач (`cg-002`, `cg-003`, `cg-004`,
`cg-006`, `cg-008`, `cg-009`) проходили проверку только на горизонте в один полуход: на горизонте 3
у них находятся другие выигрывающие первые ходы. Принимаемые наборы перегенерированы перебором,
`CheckDepth` (SGF `GX`) стал равен 3 и объявлен в описании задачи; ноль больше не ставится.
Задача `cg-004` оказалась вырожденной (на горизонте 3 выигрывает 9 ходов в окне радиуса 2 и 74
по всей доске) — удалена, вместо неё в библиотеку добавлена `cg-010` (снятие в три полухода
с единственным выигрывающим ходом; проверено на радиусах 2, 3 и по всей доске).

**Решение 4: число принимаемых первых ходов — часть API.** `Problem.AcceptedFirstMoves`,
`Problem.AcceptedFirstMoveCount`, `Problem.WeakAcceptedFirstMoveCount` (порог 3) и `Problem.IsWeak`:
задача с большим набором принимаемых первых ходов слабая, и интерфейс обязан помечать её честно.

**Решение 5: многоходовость.** Многоходовой считается задача, у которой **все** выигрывающие первые
ходы требуют не меньше трёх полуходов до цели; длина файла об этом не говорит. Для цели `Live`
критерий листа — глазная проверка `EyeDetector`, и это записано прямо: своего второго определения
глаза в слое задач нет.

**Как это проверено.** Приёмка принимающей стороны прогнана заново (`tools/accept-clean`: прежний
проверяльщик `tools/problem-prover` исполнитель отредактировал, поэтому доверия к нему нет) по всем
19 задачам с бюджетом перебора **на каждого кандидата**: расхождений нет, принимаемый набор в корне
совпадает с множеством выигрывающих ходов. Цель `dead` подтверждена отдельным инструментом
(`tools/dead-verify`): форсированный захват за заявленную границу — `nk-001` 1614 узлов, `nk-002` 1614,
`nk-003` 837, `ti-001` 25. Урок, стоивший ложного вывода: общий бюджет узлов на задачу делал
следующих кандидатов «невыигрышными», отсюда ошибочное «захват не подтверждён»; бюджет обязан
сбрасываться на каждого кандидата. В `ProblemSolver` исправлен счётчик работы: ветка `dead`
показывала `Nodes = 0`, потому что не суммировала вложенные переборы.

**Границы.** Игровые проекты (`Core`, `AI`, `AI.Onnx`, `App`) не менялись ни на строку.

## D-063. Ход соперника — в фоне, анимация видна, на телефоне есть стартовый экран

**Дата:** 2026-09-29
**Статус:** принято (замечания пользователя к версии для Android: «нет анимации хода противника и поедания камня, всё в один миг»; «нет кнопки начать матч»)

**Причина невидимой анимации — измерена, а не предположена.** Поиск хода соперника выполнялся синхронно
в потоке интерфейса: после щелчка по доске панель не обновлялась **1702 мс**, и только потом ход игрока
и ответ появлялись одним скачком. Анимация запускалась до блокировки, а её первый тик после разблокировки
сдвигал прогресс на всю длительность поиска — камень дорисовывался сразу в конечном виде. Механизм
анимации был исправен; его убивала блокировка потока.

**Решение.** Ход соперника считается в фоне (`Task.Run` вокруг синхронного селектора), результат
применяется в потоке интерфейса; ход игрока проводится и показывается сразу, поэтому доска успевает
проиграть анимацию, пока соперник думает. Интерфейс переведён на асинхронные пути
(`PlayMoveAsync`, `PassAsync`, `ApplySettingsAsync`, `StartNewGameAsync`, `LoadGameAsync`),
синхронные методы сохранены — все существующие тесты партии прошли без правок ожиданий.
Отмена (`CancelThinking`) вызывается из отмены хода, возврата, смены настроек, загрузки партии
и при переходе в режим задач; результат отменённого поиска не применяется, пока идёт поиск ходы
игрока не принимаются, «полуход» невозможен. Поиск сериализован: `Random` не потокобезопасен,
синхронный и фоновый пути не пересекаются. Длительность анимации поднята с 0,18 до 0,24 с, поставлен
тест-сторож: короче 0,2 с — падение. В режиме задач анимации не было **вовсе** (там постоянно снимаются
камни) — добавлена через `ProblemViewModel.LastCaptured` и вызов `BoardControl.Animate` в `ProblemView`.

**Стартовый экран на телефоне.** `ShellViewModel.StartOnSettings` показывает настройки до партии;
включается по режиму жизненного цикла (мобильная голова — `ISingleViewApplicationLifetime`),
настольная версия работает как прежде. Отмена настроек просто закрывает их: за ними уже готовая партия,
пустого экрана не остаётся. Платформенный код в голову не добавлялся.

**Проверка.** Мои измерения на живом приложении после правок: панель показывает ход игрока на **113 мс**,
ответ соперника приходит отдельно на **1430 мс** (было — один скачок на 1702 мс). Покадровая съёмка:
на 159 мс снятые камни полупрозрачны, на 395 мс их нет; камень игрока и камень соперника появляются
постепенно. Отмена во время раздумий оставляет «Номер хода: 0», и устаревший ход соперника не
применяется и через 3,7 с. Тесты приложения 207 → 222, домен 763 + 2 пропущенных, режимы
`--state`, `--e2e`, `--animation`, `--settings` — код 0, полный гейт с нагрузкой зелёный.

**Границы.** На телефоне не проверялось: частота кадров таймера на Android может отличаться, и если
анимация там окажется короткой, лечится тем же `DurationSeconds`. Анимация снятия в партии проверена
косвенно — тем же путём `BoardControl.Animate`, что и в задачах, где она снята покадрово. Сеттеры
смены размера и уровня из списков на панели по-прежнему считают первый ход соперника синхронно:
там возможна одна блокировка, и она оставлена сознательно, чтобы не менять поведение, на которое
опираются существующие тесты.

## D-064. Пленные камни и мёртвые группы: японский подсчёт объявлен основным

**Дата:** 2026-09-29
**Статус:** принято (жалоба пользователя: «не учёт захваченных в плен камней. Логики нет для них
в подсчёте очков и в определении территории»).

**Что было не так.** `Scorer` считал только площадь: камни на доске плюс пустые области, окружённые
одним цветом. Пленные существовали лишь как счётчик в панели и в очки не входили, а мёртвые камни
после двух пасов не снимались вовсе (канон п. 9 прямо это и предписывал). Из-за этого группа,
которую соперник уже не может спасти, продолжала приносить своему цвету очки, а её глаза — территорию;
игрок видел счёт, не совпадающий с тем, что он видит на доске.

**Основание — официальные документы, а не догадка.** Правила вида спорта «го», утв. приказом Минспорта
РФ № 815 от 05.11.2020 с изм. № 451 от 31.05.2022 (https://old.gofederation.ru/pages/361366289):
п. 1.10 — мёртвые камни снимаются и добавляются к пленникам того же цвета, полученная позиция
объявляется заключительной; п. 1.11 — территория включает пункты, «освободившиеся из-под мертвых
камней»; п. 1.12 — при японской традиции за каждого пленника и каждый снятый как мёртвый камень
начисляется очко; п. 1.13 — при китайской считаются камни на доске, а пленные не считаются;
определение «Коми» — размер коми задаёт регламент встречи. Кодекс го РФГ, ст. 13.3
(https://old.gofederation.ru/pages/1007066320) и Приложение I, пп. 2.3.1, 3.3.3
(https://old.gofederation.ru/pages/62484878). Практика РФГ 2023–2026: из 319 просмотренных регламентов
турниров «японские» названы в 158, «китайские» — в 29, в 134 система не указана; федеральные турниры
(Кубок России, Командный чемпионат России, Первенство России) — «правила подсчёта очков японские,
коми 6,5» (например, https://gofederation.ru/tournaments/792715771/statute).

**Решение.**
1. Основной объявлена японская система: очки = территория + пленные + коми белым. Китайская
   (площадь: свои камни + своя территория) считается второй величиной и показывается рядом —
   расхождение систем равно 0 или 1 очку (Приложение I, п. 3.3.3), и прятать одну из них значило бы
   прятать правду о счёте.
2. Пленные стали полноценной величиной партии: `GameState.BlackPrisoners`/`WhitePrisoners` считаются
   по ходам и восстанавливаются при отмене и возврате хода; в партию входит и число камней, снятых
   при согласовании заключительной позиции.
3. После двух пасов партия переходит в согласование: `Endgame.ProposeDead` предлагает мёртвые группы
   ограниченным поиском форсированного захвата (защита ходит первой), игрок проверяет пометки кликами
   и подтверждает подсчёт. Границы поиска объявлены прямо: неподтверждённая группа считается живой,
   спорную пометку ставит человек — движок не выдаёт догадку за доказательство.
4. Территория в обеих системах считается по заключительной позиции, то есть по доске без мёртвых
   камней; точки в сэки и на границе обоих цветов остаются нейтральными.
5. Коми не меняется: по Правилам его задаёт регламент, в приложении его выбирает игрок. Значения
   по умолчанию прежние (19×19 — 7.5, 13×13 и 9×9 — 5.5); типичное турнирное 6,5 указано в правилах
   проекта как справка, а не как навязанное значение.

**Проверка.** Приёмка по канону п. 13.9: чёрные снимают группу из трёх белых камней, два паса,
подтверждение подсчёта — японский счёт «Чёрные 6 : 5.5 Белые» (территория 3 + пленные 3), тот же
итог без пленных — «Чёрные 3 : 5.5 Белые», разница ровно 3 очка; китайская величина «Чёрные 7 : 6.5
Белые» пленных не считает. Живой прогон Lead на 1280x800: после двух пасов панель показывает
«Счёт (предварительный)», «Подсчёт не подтверждён» и кнопку «Посчитать»; после нажатия —
«Подсчёт подтверждён» и победителя; снимки `artifacts/lead-accept/endgame-counting.png` и
`endgame-confirmed.png`. Независимый живой прогон исполнителя на сохранённой партии с захватом трёх
камней дал те же числа (пленные 3, территория 3, камни 4/1, нейтрально 73, китайский 7 : 6.5).
Полный `./check.ps1` зелёный: домен 1101 + 2 пропущенных, приложение 331, десять режимов, нагрузка
16 200 ходов в 100 партиях, прирост памяти 0,6 МБ. Границы предложения мёртвых групп (до 2 дамэ,
горизонт 6 полуходов, 20 000 позиций на группу, без ко и дальних угроз) записаны в XML-доках
`Endgame.ProposeDead`; замер на 19x19 с восемью мёртвыми группами — 10 мс.

2. до первого хода кнопка называлась «Новая партия», хотя партия ещё не начата;
3. «пленные на доске не считаются. Только снятые считаются» (жалоба на показ, не на подсчёт);
4. ходы шли молча — звукового сопровождения не было;
5. подпись соперника «25 кю · MCTS с сетью 13×13 · 2 итерации» и разбор счёта на четыре строки
   с повторами «территория + пленные + камни» — непонятны рядовому игроку;
6. «игра выиграна / проиграна на десктопе — никак не подсвечивается»;
7. «размер кнопок, шрифтов в них привести в соответствие платформе и экрану».

**Решения.**

1. **Кнопка территории встала в общий ряд действий** — и в настольной панели, и в мобильной панели
   над доской. В настольном окне ряд из пяти действий (пас, отменить, вернуть, территория, новая
   партия) на 320 точках панели: цель нажатия 34 точки, кегль 12 — курсор точнее пальца.
2. **«Начать партию» до первого хода, «Новая партия» после.** Признак — `MainViewModel.IsFirstMove`:
   партия идёт и в ней нет ни одного поставленного камня. Пас и сдача камня не ставят, но партию
   завершают, поэтому одного «ходов не было» мало — проверяется и статус.
3. **Показ пленных приведён к правилам.** Правила вида спорта «го» (приказ Минспорта РФ № 815
   от 05.11.2020 с изм. № 451 от 31.05.2022): п. 1.10 — все мёртвые камни снимаются и добавляются
   к пленникам того же цвета, позиция объявляется заключительной; п. 1.11 — территория включает
   участки, «освободившиеся из-под мертвых камней»; п. 1.12 — при японском подсчёте очко даёт и
   камень, «снятый как мертвый в заключительной позиции». Проверено по официальному PDF
   (https://gofederation.ru/dl/Pravila_GO-2022.pdf, SHA-256 файла 16BC5EEA…, стр. 4; сверено слово
   в слово с base.garant.ru/74923824/ и mfgo.ru/federation/rules/). **Подсчёт в Core уже
   соответствовал правилам** — расходился только показ: строка «Пленные» брала счётчики партии,
   которые знают лишь камни, снятые ходами, а счёт уже включал снятые мёртвые. Теперь строка
   называет обе величины: «Пленные: чёрные 2 : 0 белые (в партии) · снято мёртвыми: 5 — они тоже
   в пленные и в очки». Разбор счёта при согласовании прямо говорит, что мёртвые камни идут
   в пленные, а их точки — в территорию.
4. **Звук хода.** Звук синтезируется кодом (`StoneSound`, WAV PCM 16 бит, 44 100 Гц, моно,
   120 мс ход и 130 мс снятие), а не берётся файлом: внешние ассеты в проект не добавляются,
   звук детерминирован и не занимает места. Воспроизведение — порт `ISoundPlayer`; реализации:
   `winmm.PlaySound` (Windows, WAV пишется во временный файл), внешний проигрыватель paplay/aplay/pw-play
   (Linux), `Android.Media.SoundPool` (Android), заглушка (macOS — AudioToolbox требует CoreFoundation,
   проверить негде). Звук играется ровно один раз на ход, не чаще одного раза в 60 мс, и молчит,
   если система просит не показывать анимации (`SPI_GETCLIENTAREAANIMATION`). Провал звука не может
   уронить игру: `ISoundPlayer` не выпускает исключений наружу.
5. **Тексты сокращены.** Подпись соперника — «ранг плюс понятный движок»: «25 кю · нейросеть 13×13»,
   «20 кю · перебор», «5 дан · нейросеть 19×19». Аббревиатур (MCTS), чисел итераций и «playout'ов»
   в интерфейсе нет; размер доски у сети оставлен — модель обучена под конкретный размер (D-039).
   Собственное свойство `MainViewModel.Engine` удалено: оно было вторым источником слов про движок
   и единственным местом, где оставалось «MCTS без сети». Разбор счёта стал двумя короткими строками
   («Японская: чёрные 45 : 50.5 белые · Китайская: …»), расшифровка площади показывается вместе
   с разметкой территории, а пленные и подсказка об уровнях убраны под переключатель «Подробности».
   Сообщения о сохранении и загрузке исчезают сами через 8 секунд.
6. **Итог партии виден.** Баннер над доской называет исход словами игрока («Вы победили · +7.5»,
   «Вы проиграли · −2.5», «Ничья») и красится по признаку «выиграл / проиграл / ничья»
   (`AppWin*/AppLose*/AppDraw*`); на телефоне это отдельная строка над доской, в настольной версии —
   первый блок панели; на самой доске рисуется рамка цвета итога, а не заливка: заливка делала бы
   позицию нечитаемой. Пока подсчёт мёртвых не подтверждён, баннер молчит — победитель ещё не назван.
7. **Размеры под платформу.** `PlatformMetrics.For(mobile, width, height)` — одна чистая функция
   с обоснованными константами: цель нажатия 48 точек на телефоне (палец, Android Material) и 32
   в настольном окне (курсор), кегли от 12 до 17. Мобильные правила лежат в `UiStyles.Mobile.axaml`,
   настольные — в `UiStyles.Controls.axaml`; порядок включения (общий → мобильный → настольный)
   записан в `App.axaml`, потому что при равном приоритете в Avalonia побеждает последнее правило.
   Ряд действий телефона разбит на две строки: четыре действия партии и «Начать партию» с кнопкой
   «Файл» (сохранить и загрузить), потому что пять кнопок в 360 точек не помещались.

**Проверка.** Домен — 1101 тест, приложение — 392; `check.ps1` зелёный; живые прогоны Lead на 360×784
и в настольном окне (скриншоты в `artifacts/lead-accept/`). Отдельно: 28 тестов метрик платформы,
37 тестов звука, тесты строк состояния и баннера итога. Проверка правил РФ — `TASKS/T-E-rules-verification.md`
(цитаты пунктов, машинные числа, что показывать игроку).

**Границы.** Сила уровней не измерялась и не менялась; звук на macOS — тишина (заглушка);
системная настройка «уменьшить движение» читается только на Windows.

## D-066. Пять замечаний после живой игры 2026-10-02: подсчёт, старт партии, обновления и задачи

**Дата:** 2026-10-02
**Статус:** принято (пять жалоб пользователя после партии и разбора задач).

**Что не устраивало.**

1. «При нажатии территория — показывать правильный подсчёт территории и пленных. Сейчас это
   реализовано костылями: при завершении партии появляется сообщение "Проверьте мёртвые группы…
   Окончательный счёт — по кнопке" с кнопкой "Посчитать". До этого момента подсчёт территории
   и пленных на доске ведётся некорректно».
2. «Кнопка "Начать партию" должна ознаменовать старт игры — это начало подсчёта времени партии.
   Должна появиться кнопка пауза. И отменить партию. Интерфейс на андроиде привести к более
   современному виду. Учитывая эти кнопки. Они должны работать, а не быть пустышкой».
3. «При запуске игры делать проверку на обновление и сообщать пользователю о новой версии
   с вариантами "обновить сейчас" и не сейчас/позже. Добавить анимацию скачивания/установки
   на всех платформах».
4. «Выпадающий список "Условия и Источник" сейчас без единой ширины. Оставить только "Условия"».
5. «Текст удали в условиях — он не несёт полезной информации… И убери значения кю в задачах».

**Что нашла разведка (доказано чтением кода и тестами, ревизия 17228f7).**

- **Рамка итога на доске рисовалась с первого хода.** `MainViewModel.ResultTone` читал
  `CurrentScore.Winner` и не смотрел на статус партии, а `BoardView.RefreshOutcomeHighlight`
  применял её без проверок. На пустой доске победитель по коми — белые, поэтому играющий чёрными
  сразу видел рамку проигрыша. Это и есть «подсчёт на доске ведётся некорректно» в самом заметном виде.
- **Счёт середины партии назывался окончательным:** пометка «предварительный» ставилась только
  в согласовании, а не всю партию.
- **Сдача называлась по счёту доски, а не по сдаче:** `Outcome` брал победителя из счёта, а не
  из `GameState.Finish()`, поэтому сдавшийся при перевесе объявлялся победителем.
- **Разбор площади не сходился со счётом:** строка «камни 5 + территория 3» стояла рядом
  с японским счётом 11, в котором те же пленные — слагаемое; пленных в разборе не было.
- **Числа подсчёта прятались в свёрнутых «Подробностях»:** нажатие «Территория» показывало разметку
  на доске, но не числа.
- **«Начать партию» была той же кнопкой, что «Новая партия»,** отдельного старта не существовало,
  а партия шла с момента создания модели (если игрок играл белыми, соперник ходил до нажатия).
- **Баннер итога был мёртв на обеих раскладках:** `GameResultBanner` получал модель только через
  конструктор с параметром, а разметка создавала его без параметров, поэтому `Refresh()` выходил
  сразу, баннер не показывался, а его кнопка «Новая партия» не была подписана. То есть D-065 §6
  «Итог партии виден» на экран не дошёл.
- **Проверки обновления при запуске не было вовсе,** а прогресса скачивания — ни в каком виде.
- **В задачах заголовок раскрывающегося списка и его содержимое имели разную ширину** (тема Fluent
  задаёт `Expander` выравнивание `Left`), а подсказка режима и происхождение решения повторялись
  у каждой задачи.

**Решения.**

1. **Подсчёт.** Территория и пленные считаются по одной доске подсчёта (`Endgame.ClearedBoard`),
   предложение мёртвых групп считается **один раз на позицию** (кэш по экземпляру доски, шов
   `DeadProposalCount`) — геттеры счёта больше не запускают перебор на каждое чтение. Строка пленных
   стала одной величиной с разложением: «Пленные: чёрные 2 : 0 белые (в партии 0 : 0 · мертвыми 2 : 0)».
   Японская строка называет слагаемые прямо: «чёрные 6 (территория 4 + пленные 2) : 5.5 белые
   (территория 0 + пленные 0 + коми 5.5)»; китайская остаётся площадью. Разбор площади сокращён
   до двух строк («Территория — …», «Камни — …») и стоит рядом с кнопкой «Территория», а не
   в свёрнутых «Подробностях». Согласование мёртвых групп остаётся (правила РФ, D-064), но перестало
   выглядеть ошибкой: заголовок «Согласование подсчёта», строка «Проверьте пометки мёртвых групп»,
   счёт «Предварительный счёт: …», кнопка «Посчитать» доступна сразу.
2. **Рамка итога и счёт.** `ResultTone` возвращает `GameTone.None`, пока итог не назван (партия идёт
   или идёт согласование); счёт середины партии и согласования подписан предварительным; сдача
   и завершение по лимиту ходов называют победителя из `GameState.Finish()`, а не из счёта доски.
   Строка счёта печатается инвариантно, чтобы разделитель дроби не зависел от культуры машины.
3. **Старт партии и часы.** Новая служба `GameClock` (`TimeProvider`, по умолчанию `AppLog.Time`):
   старт, пауза, продолжение, остановка, сброс, строка «ММ:СС». Модель представления получила
   `IsGameStarted/IsGameRunning/IsGamePaused/ClockDisplay/CanTogglePause/CanAbortGame/CanPlayMove`
   и методы `StartGame/PauseGame/ResumeGame/AbortGame` (и фоновые версии); пауза настоящая — ходы
   и пас отклоняются, поиск соперника отменяется. «Отменить партию» возвращает состояние «партия
   не начата»: часы на нуле, ходы очищены. Одна кнопка на два состояния — «Пауза» / «Продолжить».
   В обеих раскладках появилась строка времени и эти две кнопки; на телефоне она первая в панели
   действий, потому что строка состояния на низком экране прячется.
4. **Обновления.** Проверка идёт при первом показе оболочки, в фоне и молча: отказ (нет сети,
   нет манифеста) — ожидаемый исход и пишется только в журнал. Приглашение — полоса под строкой
   режимов, а не модал поверх доски: «Доступна версия X — у вас Y» с кнопками «Обновить сейчас»
   и «Позже». Прогресс честный по байтам (`IProgress<DownloadProgress>`, чтение порциями по 80 КиБ),
   состояния «Скачивание… N%», «Установка…», «Готово», «Не удалось: причина», рабочая «Отмена».
   Настройки и приглашение используют одну модель (`App.Updates`), поэтому состояния не расходятся.
5. **Задачи.** Заголовок «Условие», содержимое и переключатель растянуты на ширину панели
   (`HorizontalAlignment`/`HorizontalContentAlignment` = `Stretch` для `Expander`). Убраны подсказка
   режима и строка о происхождении решения (вместе со свойствами `Guide`/`SourceText`/`HasSource`
   и привязками), из подписей списка убрано «· N кю»; вид задачи остаётся названным один раз
   («ts-001 · по решению источника»), потому что исход движком не доказан и игрок обязан это видеть.
   Поле `Problem.Rank` и аннотация SGF `GD` не удалены: они данные библиотеки и проверяются тестами.

**Проверка.** `check.ps1` зелёный целиком: сборка без предупреждений, домен **1103 + 2 пропущенных**,
приложение **468**, четырнадцать режимов (в гейт добавлены `--territory`, `--clock`, `--update`;
`--render-territory` пишет картинку заключительной позиции), нагрузка 16 200 ходов в 100 партиях.
Новые тесты: `GameClockTests` (11), `GameFlowTests` (13), `GameResultBannerTests` (14),
`UpdateViewModelTests` (12), дополнены `TerritoryTests`, `EndgameScoreTests`, `GameStatusLinesTests`,
`ScoringRuleTests`, тесты обновлений. Картинка подсчёта — `artifacts/lead-accept/endgame-territory.png`.

**Границы.** Живого окна в сессии проверки не было (сессия без графической сессии): вид проверен
тестами вида, безоконными режимами и снимком рендера, но глазами на экране — нет. Баннер итога
ожил, однако его вид на телефоне (карточка занимает около 130 точек над доской) не смотрели.
Реальную установку обновления (Inno Setup на Windows, системный установщик APK) и реальную сеть
не проверяли — только подставной сервер. Предложение мёртвых групп осталось ограниченным
(до двух дамэ, шесть полуходов, без ко): это граница доказательства, а не обещание.

## D-067. Фаза 13: рефакторинг после пяти замечаний

**Дата:** 2026-10-02
**Статус:** принято (просьба пользователя «после завершения всех заданий проведи профессиональный
рефакторинг проекта»).

**Контекст.** Пять замечаний 2026-10-02 (D-066) закрыты быстро и в одних и тех же файлах: `MainViewModel`
дорос до 1485 строк, `BoardView.axaml.cs` — до 1175, `CheckModes` — до 667, в головах появились три
новых проверочных режима, в разметке накопились правила без применения, а в тестах — по три
одинаковых подставных объекта. Правило фазы то же, что у фаз 10 и 11: **поведение не меняется** —
ни правил, ни текстов интерфейса, ни чисел, ни имён публичных членов.

**Что сделано (шесть срезов).**

1. **Мёртвые правила стилей.** Проверка «какой класс разметки где применён» нашла четыре правила,
   которые не мог применить никто: `Button.app-action-bar` (объявлено дважды — в общем и мобильном
   файле, а ряд действий помечен `app-touch`), `TextBlock.app-title`, `StackPanel.app-action-row`
   (класс стоит на `Grid`, а селектор — на `StackPanel`). Удалены.
2. **Списки свойств вида.** `OnViewModelPropertyChanged` сверял имена свойствами `is … or …` — 27 имён
   в четырёх ветках, и один и тот же `RefreshSummary()` стоял в двух из них. Имена собраны в два
   статических списка (`PanelProperties`, `ComboProperties`), добавлен тест: имена обязаны существовать
   у модели представления, списки не пересекаться, а минимум «без чего панель застывает» — на месте.
3. **Таблица проверочных режимов.** В точке входа было 110 строк цепочки `if (args.Contains(…))`.
   Режимы собраны в таблицу `ModeRunner`: у каждого названы ключ, что он проверяет и что делает,
   поэтому новый режим нельзя добавить, забыв описание, а `Program.Run` снова занимается запуском.
4. **Согласование подсчёта** вынесено из `MainViewModel` в `ScoringAgreement` (301 строка): пометки
   мёртвых, кэш «одно предложение на позицию», ревизия для перерисовки, подтверждённый итог и доска
   подсчёта. Итог по-прежнему считает партия — служба получает делегат, а не `GameState`.
   `MainViewModel`: 1485 → 1382 строки, 28 новых тестов на саму службу.
5. **Проверочные режимы головы.** `ClockCheck` и `UpdateCheck` вынесены из `CheckModes` (667 → 480 строк);
   методы остались тонкими делегатами, поэтому точка входа и аргументы не менялись. Общий помощник
   `Expect` остался один — его текст «не выполнено: …» видит человек.
6. **Числа темы стали проверяемыми.** В шапке `UiTheme.axaml` написано, что расхождение с
   `PlatformMetrics.For` — ошибка, а не настройка, но проверить это было нечем. Теперь файл темы
   приходит в тесты ссылкой, и тест сверяет цель нажатия, кегли, радиусы, отступы и высоты полос.
   Общий `AppTouchTarget` (48 точек, палец) намеренно не сверяется с настольной веткой: настольные
   размеры живут литералами в стилях — так и написано в теме.

**Подставные объекты в тестах.** Три реализации `HttpMessageHandler`, два сборщика отчётов о загрузке
и локальные часы переехали в `Support/`: `StubHttpHandler`, `CollectingProgress`, `FakeTime`.

## D-068. Живой подсчёт территории: мёртвые группы определяет программа — по запросу оценки

**Дата:** 2026-10-02
**Статус:** принято (жалоба пользователя №1 вечера 2026-10-02; T-039, задача task-1)

**Что не устраивало.** «По кнопке Территория я должен увидеть территорию принадлежащую камням
с учетом мертвых групп на доске (отнесенные в пленные сопернику). Чтобы в режиме игры я мог
посмотреть перспективы партии на столе. Определять мертвую группу должна программа, а не человек.
Программа знает правила». На ревизии `a31763f` перебор предлагал мёртвых только после двух пасов
(`ScoringAgreement.ProposedDead` звал `Endgame.ProposeDead` лишь при `FinishedByTwoPasses`),
а переключатель «Территория» существовал только в идущей партии: в игре мёртвых не учитывал никто,
после конца партии кнопка исчезала.

**Решение.**

1. **Мёртвые группы определяет программа** — тем же ограниченным перебором форсированного захвата
   (`Endgame.ProposeDead`: группы не более чем с двумя дамэ, горизонт 6 полуходов, 20 000 узлов
   на группу). Это граница доказательства, а не правило: ложное «мёртвая» не выдаётся никогда,
   непроверенное считается живым.
2. **Перебор идёт по запросу оценки.** Признак — `HasTerritory` (игрок включил разметку территории
   или партия не идёт); `ScoringAgreement.Sync(board, status, estimateRequested)` держит признак
   в ключе кэша «один перебор на позицию». Пока оценка не запрошена, `DeadPoints` пуст, а
   `DeadProposalCount` не растёт. Почему не «всегда»: замеры дали на 19×19 22 мс в середине,
   101 мс на 200-м ходу, 258 мс на 350-м и до 3,6 с на плотной доске, а панель читает счёт после
   каждого хода — постоянный перебор стал бы заморозкой на каждом ходу.
3. **Территория, счёт и пленные считаются по доске без помеченных мёртвых**
   (`ScoringBoard = Endgame.ClearedBoard`): снятый камень уходит в пленные соперника, его точка
   становится территорией снявшего. В `Core` это было и раньше (D-064, D-066) — теперь это видно
   и в идущей партии.
4. **Кнопка «Территория» доступна, когда на доске есть хоть один камень** (`CanToggleTerritory = !IsFirstMove`):
   и в игре, и после конца партии; до первого хода скрыта — на пустой доске территории нет.
   В ряду действий она остаётся на месте и лишь становится недоступной: скрытая кнопка оставляла
   четвёртую колонку пустой (жалоба №2б).
5. **Ручной клик перекрывает перебор.** Пометка и снятие пометки кликом — истина в последней
   инстанции для позиции; снятая кликом программная пометка не возвращается пересчётом.

**Предохранители (замеры).** Два бюджета узлов на одно предложение: `EstimateNodesPerPosition = 40 000`
(оценка в идущей партии) и `MaxNodesPerPosition = 150 000` (окончательное предложение при согласовании
и конце партии); `MaxNodesPerGroup = 20 000` не менялся. Бюджет — предохранитель от патологической
доски, а не ограничитель качества: на корпусе из 61 позиции (8 расстановок правил, 5 цумэго, 36 задач
библиотеки, 12 позиций партии 19×19 AI против AI до двух пасов) оба бюджета дали списки, совпадающие
с `ProposeDead(board, int.MaxValue)` камень в камень — расхождений 0/0. Самая дорогая позиция корпуса —
7 761 узел: запас 5,2× у оценочного бюджета и 19,3× у окончательного.

**Числа оценки в игре.** 9×9 — до 19 мс, 13×13 — до 99 мс, 19×19 — медиана 70 мс, плотная поздняя
партия до ~2 с. `CandidateLiberties = 2` оставлен: эксперимент с 3 не добавил ни одной метки
на корпусе, но ухудшил время (100 ходов 22 → 54 мс, заполненная доска 66 → 3 597 мс).

**Что проверено.** Режим `--territory` проверяет идущую партию без оценки (0 пометок, 0 переборов),
идущую партию с оценкой (перебор сам помечает мёртвую группу; территория, пленные и счёт согласованы),
выключение оценки, согласование и подтверждение, доступность переключателя, сумму
«территория + камни + нейтраль = площадь доски» и ту же арифметику на 13×13 и 19×19. Ложных «мёртвых»
не нашлось на провокационных позициях: два глаза, сэки, гонка дамэ, группа в атари.

**Границы.** Ко и дальние угрозы перебор не доказывает — такая группа не будет помечена (её помечает
игрок кликом). Цена узла перебора на 19×19 — 250–300 мкс (дорогие `DefenseMoves`/`IsLegal`):
оптимизация `Core/Scoring` — отдельная задача, поэтому оценка плотной поздней партии 19×19 может
заморозить окно до ~2 с. Для 9×9 (размер игры пользователя) оценка стоит миллисекунды.

## D-069. Вид: сообщения по центру экрана, панель действий по доске, один счёт на экран

**Дата:** 2026-10-02
**Статус:** принято (жалобы пользователя №2а, 2б, 2в вечера 2026-10-02; T-039, задача task-2)

**Что не устраивало.** (а) «Вывод блока с сообщением сверху (где Вы проиграли\выйграли, вышло
обновление и т.п.) должно быть в центре экрана»; (б) «блок с кнопка (пас отменить и т.д.) наезжает
на доску и сделан не аккуратно»; (в) «дублирование счетов: на скрине видно втором… показывать счет
и подробно — с разъяснениями откуда что посчиталось».

**Решения.**

1. **Сообщения — карточкой по центру экрана** на затемнении из темы (`AppOverlayBrush`). Баннер итога
   один на обе раскладки: раньше их было два (настольный первым блоком панели, мобильный отдельной
   строкой сетки над доской) и оба стояли полосой. У карточки итога две кнопки — «Новая партия»
   (primary) и «Закрыть»: вторая нужна, чтобы посмотреть итоговую доску; закрытие держится, пока итог
   тот же, и снимается следующим завершённым итогом. Хост приглашения обновления (`ShellView.UpdateHost`)
   растянут на все три строки оболочки, затемнение нажатий не ловит (`IsHitTestVisible = False`):
   иначе «Позже»/«Отмена» оказались бы недоступны, а во время «Установка…» кнопок нет вовсе — игрок
   остался бы заперт.
2. **Панель действий телефона — по ширине доски.** Ширину считает чистая функция
   `BoardLayoutRules.MobileActionBarWidth`: не шире отведённого места и не уже читаемых 320 точек.
   Четыре равные колонки, ряд заполнен всегда («Территория» остаётся на месте и лишь становится
   недоступной), зазор между доской и панелью — 8 точек, отступы симметричны. Настоящая причина
   «наезда» — не наложение, а пересчёт: строка доски меняла высоту, ширина панели не пересчитывалась;
   теперь вид подписан на `SizeChanged` строки доски.
3. **Каждая величина — один раз на экран.** Счёт: `DesktopScoreText` (настольная панель) и
   `SheetSummary` (свёрнутая шторка телефона); `DesktopScoreDetailText` и `MobileScoreText` удалены.
   Объяснение «откуда что посчиталось» — один раз, в «Подробностях» (`DesktopScoreSystemsText`,
   `MobileScoreDetailText`): обе системы со слагаемыми, мёртвые группы, нейтральные точки.
   Баннер больше не повторяет счёт: `ResultDetail` — только исход словами. Пленные на телефоне —
   один раз, в свёрнутой шторке (`MobilePrisonersText` из подробностей убран).

**Проверка.** Тесты вида считают вхождения строки счёта и объяснения в логическом дереве каждой
раскладки (ровно одно), проверяют отсутствие удалённых имён, полноту и равенство колонок ряда действий,
центровку карточки, растянутость затемнения и то, что баннер лежит поверх обеих раскладок. Живая
проверка — стенд `tools/verify-ui2` (окно 936×759 и 380×780, снимки в `artifacts/verify-ui2/`).

**Границы.** Реальные пиксели раскладки без окна не измеряются: `Avalonia.Headless` в проект
не добавлен, а новых пакетов проект не заводит. Поэтому правила раскладки проверены как чистые
функции, структура разметки — тестами вида, а положение и перекрытия — живым стендом.

## D-070. Оценка без подтверждения: мёртвые группы считаются всегда, итог называется сразу

**Дата:** 2026-10-02
**Статус:** принято (сообщение пользователя вечером 2026-10-02, после первой итерации T-039;
отменяет часть D-068 §2 и §4)

**Что не устраивало.** К сообщению приложен снимок панели «Проверьте пометки мёртвых групп: клик
по камню помечает или снимает пометку. [Посчитать]», и текст: «Ты можешь подсчитывать мертвые
группы без этого сообщения с кнопкой? Нужна твоя оценка в любой момент игры. Я не хочу ещё куда-то
тыкать, чтобы ты смог показать мне состояние доски».

**Решение.**

1. **Шага подтверждения нет.** После двух пасов итог называется сразу: мёртвые группы определяет
   программа, счёт, победитель и баннер показываются немедленно. Панели согласования (приглашение
   и кнопка «Посчитать») убраны из обеих раскладок, а вместе с ними — мёртвый API
   (`IsCounting`, `CanConfirmScore`, `ConfirmScore`, `ApplyRule`, ветка подсчёта в строках вида).
   Согласование по правилам РФ (D-064) остаётся по существу — но его проводит программа,
   а не игрок кнопкой.
2. **Оценка постоянная.** Признак «оценка запрошена» из D-068 §2 отменён: предложение мёртвых
   считается для любой позиции, кэш — один перебор на позицию. Бюджет выбирается по состоянию
   партии: в игре оценочный предохранитель (40 000 узлов), после конца — окончательный (150 000).
3. **Разметка показывается сразу.** `ShowTerritory` по умолчанию истинно: крестики мёртвых
   и знаки территории видны без нажатий и в игре, и после конца партии. Переключатель
   «Территория» остаётся и работает выключателем для тех, кому разметка мешает; на оценку
   он не влияет.
4. **Право поправить остаётся.** Клик по камню после конца партии помечает или снимает пометку
   группы, и названный итог пересчитывается сразу — но это право, а не обязанность.

**Цена постоянной оценки — ускорение перебора.** Горячий путь `DeadGroupSearch` переписан:
примерочный ход — мутация локальной копии камней с откатом вместо новой доски (`ApplyMove`/`Clone`),
проверка легальности с ранним выходом, таблица соседей вместо итераторов, отметки-поколения вместо
`HashSet`/`Queue`, один перебор на позицию с общими буферами, кэш группы по версии позиции.

| Размер | µs на узел (было → стало) | Максимальный вызов | Медиана |
|---|---|---|---|
| 19×19 (467 ходов) | 166,3 → **11,0** (15×) | 2017 → **93 мс** (22×) | 65 → 4 мс |
| 13×13 (188 ходов) | 74,5 → **13,0** (5,7×) | 104 → **5 мс** (21×) | 16 → 1 мс |
| 9×9 (107 ходов) | 45,5 → **5,0** (9,1×) | 20 → **2 мс** (10×) | 6 → 1 мс |

**Доказательство неизменности.** Корпус 61 позиции (8 расстановок правил, 5 цумэго, 36 задач
библиотеки, 12 контрольных точек партии 19×19): списки предложенных мёртвых совпали камень
в камень до и после ускорения. Закреплено постоянным тестом `DeadProposalCorpusTests`
(ходы партии хранятся строкой и воспроизводятся, ожидаемые списки — таблицей).

**Проверка.** `./check.ps1 -SkipStress` зелёный: домен 1116 + 2 пропущенных, приложение 579/579,
режим `--territory` проверяет идущую партию (пометки есть сразу, разметка показана, бюджет оценки),
скрытие разметки (пометки и счёт не меняются), конец партии (итог назван сразу, кнопки нет,
клик меняет счёт), 13×13 и 19×19, сумму по площади доски.

**Границы.** Пометки — по-прежнему доказательство, а не догадка: ко и дальние угрозы не
доказываются (группа остаётся живой), ложное «мёртвая» не выдаётся. Худший одиночный вызов теперь
93 мс на 19×19 (было 2017 мс) — постоянная оценка укладывается в кадр на всех размерах.

## D-071. Разметка — по кнопке, меню — по центру, список задач — в главном окне

**Дата:** 2026-10-03
**Статус:** принято (три замечания пользователя от 2026-10-03; уточняет D-070 §3 и D-066 §1)

**Что не устраивало.** Скриншот телефона в идущей партии: на доске крестики мёртвых групп и знаки
территории стоят без нажатия, панель показывает «Предварительный счёт: Чёрные 22 : 16.5 Белые».
Замечания: «показывать мертвые группы камней на доске (крестики на скриншоте) — только по кнопке
территория»; «кнопки из окна "Партия": "новая партия", из кнопки "ещё": "отменить партию",
"сохранить партию", "загрузить партию", "настройки" — перенести в отдельное всплывающее по центру
экрана, под названием "меню". Отдельную кнопку внизу под неё сделать рядом с "Партия", "Задачи",
"Настройки"»; «в задачах: вытащить выпадающий список с перечнем задач "Задача" из выпадающего списка
"Условия" в главное окно задач, под условие».

**Решения.**

1. **Разметка доски — только по кнопке.** Крестики мёртвых групп и знаки территории рисуются,
   лишь когда включён переключатель «Территория»: `ShowTerritory` по умолчанию `false`,
   `HasTerritory => ShowTerritory` (дизъюнкция «|| партия не идёт» из D-070 §3 убрана — в конце
   партии разметка сама не появляется). **Перебор мёртвых при этом идёт всегда, и числа считаются
   всегда**: `ScoreBreakdown` больше не зависит от переключателя, поэтому «Территория — …»,
   «Камни — …», счёт и пленные видны без нажатий. Правило простое: нажатий требует картинка,
   а не оценка.
2. **Меню телефона.** «Новая партия» («Начать партию» до первого хода) и пункты прежней кнопки
   «Ещё» — отменить партию, сохранить, загрузить, настройки — собраны в карточку «Меню» по центру
   экрана на затемнении (та же форма, что баннер итога). Четвёртая кнопка нижней навигации «Меню»
   открывает карточку и раздел не переключает; пункты зовут прежние обработчики, второй логики нет.
   Вторая строка панели действий убрана: в ряду остались четыре действия партии (пас, отменить,
   вернуть, территория), панель стала ниже и ровнее. Настольная раскладка не менялась — там меню-бар
   окна и своя панель.
3. **Список задач — в главном окне.** В режиме задач список задач вынесен из «Условия» в главное
   окно панели, сразу под условие: условие читают, задачу выбирают — прятать выбор в свёртку незачем.

**Проверка.** `./check.ps1` (с нагрузкой) зелёный: домен 1116 пройдено + 2 пропущенных,
приложение 591/591, двенадцать безоконных режимов, нагрузка 16 200 ходов в 100 партиях,
прирост памяти 0,6 МБ (лог `artifacts/lead-gate3.txt`). Тесты вида: разметка выключена по умолчанию

## D-072. Движок не кормит мёртвые группы; настройки — экран, старт — с меню

**Дата:** 2026-10-03
**Статус:** принято (шесть правок пользователя 2026-10-03; дополняет D-070 и D-071)

**Что не устраивало.** Снимки телефона (13×13): «проблема с логикой противника: противник снова ходит
себе в убыток… нет смысла ставить камни к своим мертвым группам, тем самым добавляя пленных
противнику»; «в начале матча загорается кнопка территория, которая не отключается»; «сделать
полноценным окно настроек, а не всплывающим окном»; «окно меню должно быть первым активным окном
над партией — сейчас первое окно при запуске это настройки»; «настройки разбить на несколько
подразделов»; «при выборе из меню новая партия — должна выводится настройка партии»; «из настроек
убрать кнопку начать партию».

**Решения.**

1. **Правило пленных** (`AI/Selectors/PrisonerPolicy.cs`): ход отбрасывается, если он примыкает
   к своей **доказанно** мёртвой группе (`Endgame.ProposeDead`) или лежит в территории соперника
   на доске без доказанно мёртвых камней (`Scorer.Ownership`). Исключение — только ходы, которые
   что-то дают: снятие камней и спасение **живой** группы из атари. Когда отброшены все ходы —
   пас: законный ход, который ничего не кормит. Правило включается **только там, где перебор
   уже что-то доказал**: в открытой позиции «владение» означало бы, что первый камень забирает всю
   пустую доску, и любой ход выглядел бы убыточным (промежуточная версия пасовала в дебюте —
   это поймали `EndgameSelectionTests` и `TacticalGuardSelectorsTests`). Единая точка отбора —
   `AI/Selectors/MovePolicy.cs`: сначала «не доедать свою территорию» (`EndgamePolicy`), затем
   «не кормить пленных»; проведена в эвристику, MCTS (обе ветки) и случайный уровень.
2. **Настройки — полноценный экран с тремя подразделами** (`SettingsView`): «Партия» (размер доски,
   уровень AI, цвет, коми, звук), «Подсчёт» (японская «для РФ» и китайская, пояснения к каждой
   и «чем отличаются»), «О программе» (версия, загруженные модели, логи, проверка обновления).
   На телефоне это экран во всю ширину, а не карточка поверх доски; настольная версия показывает
   тот же вид в окне `SettingsWindow`. Кнопки «Начать партию» в настройках нет: настройки —
   настройки, а не старт партии.
3. **Что применяется когда.** Правило подсчёта и звук — сразу (строка счёта и победитель меняются
   в текущей партии). Размер доски, уровень, цвет и коми — в новой партии; об этом прямо говорит
   подсказка в подразделе «Партия».
4. **«Новая партия» из меню открывает настройки** на подразделе «Партия»; закрытие («Готово»)
   применяет выбор и начинает партию заново. Вход из раздела «Настройки» партию не пересоздаёт.
   Разницу держит один признак в `BoardView` (`FinishSettings`).
5. **Старт: первым окном — меню.** Признак `startOnSettings` (мобильная версия открывалась
   на настройках) удалён. На телефоне при запуске показывается карточка «Меню», раздел «Партия»;
   в настольном окне карточки нет — там меню-бар и мышь. Решение принимается один раз по первому
   настоящему размеру вида (нулевой размер дал бы «настольную» раскладку по ошибке).
6. **«Территория» в начале партии** выключена и недоступна, пока на доске нет камней
   (`ShowTerritory = false`, `CanToggleTerritory = !IsFirstMove`) — подтверждено тестами, правки
   не потребовалось: в 0.2.52 это уже было так.
7. **Тесты вида идут по очереди** (`[assembly: CollectionBehavior(DisableTestParallelization = true)]`
   в `App.Tests/TestParallelization.cs`): статический `Avalonia.Utilities.WeakEvents` не потокобезопасен,
   и параллельное построение разметки (SettingsView внутри BoardView) ломало общий список подписок —
   отсюда случайные `Stack empty`, NRE и `ArgumentOutOfRange` в разных тестах. Прогон по очереди
   занимает столько же времени (≈13 с) и даёт стабильные 626/626.

**Проверка.** `./check.ps1` (с нагрузкой) зелёный: домен 1133 пройдено + 2 пропущенных,
приложение 626/626, двенадцать безоконных режимов, нагрузка 16 200 ходов в 100 партиях,
прирост памяти 0,6 МБ (лог `artifacts/lead-gate4.txt`). На позиции жалобы (13×13, белый блок 3×3
доказанно мёртв): легальных ходов 154, после правила разрешено 0 — движок пасует, пленных белых
не прибавляется (было 10 снятых вместо 9). Три «золотые» партии сдвинулись ровно на один ход каждая —
тот, где движок играл в дамэ своего мёртвого камня (23/24, 11/24 и 13/24 совпавших ходов). Тесты AI
на силу, цумэго, лестницу уровней и матрицу силы зелёные без правок.

**Что нашла независимая проверка (и что из этого вышло).** Два дефекта, оба в настольном пути
настроек, оба закрыты до выпуска.

1. **Смена системы подсчёта в настольном окне не доходила до партии.** `SettingsWindow` создаёт
   собственный экземпляр `SettingsView`, а на событие `ScoringRuleChanged` был подписан только вид
   внутри `BoardView` (телефонный путь), поэтому в окне выбранное правило уходило в партию лишь
   при закрытии. Исправлено: событие несёт само выбранное правило (`EventHandler<ScoringRule>`),
   а применение вынесено в один общий шов `SettingsView.ApplyScoringRuleOnChange(settings, game)`,
   который зовут оба хозяина настроек — `BoardView` и `MainWindow` (через `internal SettingsWindow.Settings`).
2. **Закрытие настольного окна настроек пересоздавало партию.** Окно применяло настройки через
   `ApplySettings`, то есть начинало новую партию: игрок открывал настройки, менял только правило
   подсчёта — и его партия стиралась. Исправлено: закрытие сохраняет выбор и запоминает его
   (`MainViewModel.RememberSettings`, без `BeginGame` и без уведомлений), но партию не трогает;
   новая партия начнётся с выбранными значениями. Правило подсчёта и звук по-прежнему применяются
   сразу. Итог один для обеих раскладок: **настройки никогда не начинают партию — её начинает игрок.**

**Проверка (финальная ревизия).** `./check.ps1` (с нагрузкой) зелёный: домен 1133 пройдено
+ 2 пропущенных, приложение 631/631, двенадцать безоконных режимов, нагрузка 16 200 ходов
в 100 партиях, прирост памяти 0,6 МБ (лог `artifacts/lead-gate6.txt`).

## D-073. Настройки: один источник значений и явные «Сохранить» / «Отмена»

**Дата:** 2026-10-03
**Статус:** принято (две правки пользователя 2026-10-03; уточняет D-072 §2–4)

**Что не устраивало.** Снимок настольного окна: диалог настроек показывает «Уровень AI: 25 кю»,
а панель партии за ним — «10 кю · нейросеть 13×13». «Не синхронизирован уровень AI… Непонятно кто
играть будет. В новых настройках не хватает кнопки сохранить настройки и отмена, в настройках партии
и настройках подсчёта».

**Причина.** Настройки жили **в трёх копиях**, и каждая обновлялась сама: `MainViewModel._settings`
(из неё панель берёт уровень, коми, цвет и размер), `BoardView._settings` (для мобильного экземпляра
вида настроек) и `MainWindow._settings` (именно оно уходило в диалог). Смена уровня списком в панели
не была видна диалогу.

**Решения.**

1. **Один источник значений — модель представления.** `MainViewModel.Settings` — текущие настройки
   партии; из них панель берёт уровень/коми/цвет/размер, их же показывают и мобильный экран настроек,
   и настольный диалог (`new SettingsWindow(ViewModel.Settings, …)`). Копии в `BoardView` и `MainWindow`
   удалены; у вида остался только снимок «как было при открытии» — для «Отмены».
2. **Явные «Сохранить» и «Отмена»** в низу экрана настроек (видны в обоих подразделах — «Партия»
   и «Подсчёт»). «Готово» из заголовка убрано, крестик настольного окна означает «Отмена»,
   переход в другой раздел — тоже отмена.
3. **Что делает «Сохранить».** Приводит партию в соответствие с выбором, чтобы вопрос «кто будет
   играть» не возникал: уровень AI начинает играть со следующего хода соперника **без пересоздания
   партии**; смена размера доски, цвета игрока или коми начинает новую партию; правило подсчёта
   и звук применяются сразу. Файл настроек перезаписывается.
4. **Что делает «Отмена».** Ничего не сохраняет — ни в файл, ни в партию — и возвращает то, что
   действует мгновенно (правило подсчёта и звук) по снимку на входе. Из меню «Новая партия»
   «Сохранить» начинает партию, «Отмена» возвращает к текущей.

**Проверка.** `./check.ps1` (с нагрузкой) зелёный: домен 1133 пройдено + 2 пропущенных,
приложение 642/642, двенадцать безоконных режимов, нагрузка 16 200 ходов в 100 партиях,
прирост памяти 0,6 МБ (лог `artifacts/lead-gate7.txt`). Независимая проверка живого окна:
уровень в настройках совпадает с уровнем партии; «Сохранить» меняет уровень в панели, не пересоздавая
партию; смена размера доски начинает новую партию (9×9 → 13×13, камней 0); «Сохранить» меняет систему
подсчёта сразу; «Отмена» и «Сохранить» видны в обоих подразделах, «Отмена» и крестик окна оставляют
партию и уровень без изменений. На позиции жалобы (13×13,
белый блок 3×3 доказанно мёртв): легальных ходов 154, после правила разрешено 0 — движок пасует,
пленных белых не прибавляется (было 10 снятых вместо 9). Три «золотые» партии сдвинулись ровно
на один ход каждая — тот, где движок играл в дамэ своего мёртвого камня (23/24, 11/24 и 13/24
совпавших ходов). Тесты AI на силу, цумэго, лестницу уровней и матрицу силы зелёные без правок.

## D-074. Задачи: подпись «номер · название», формулировка — в «Цель», служебные пометки убраны

**Дата:** 2026-10-04
**Статус:** принято (три замечания пользователя 2026-10-04; T-043)

**Что не устраивало.** «1) Требуется в выпадающем списке задач в "Задачи" - сделать номер задачи,
название задачи. Сейчас это ts-001*по решению источника*решение источника. 2) Данные условия
перенести в Цель. Условие убрать. Сейчас это выглядит так: Цель: по решению источника. А в условия
истинная цель задачи. 3) оставшиеся бессмысленные надписи "по решению источника" \ "решение
источника" \ "движком не проверялось" - ликвидировать.»

**Причина.** Подпись списка собиралась из вида задачи (`Goal.Descriptions`), а не из названия:
у всех 36 задач библиотеки это «по решению источника», и подпись не различала задачи. Строкой
«Цель» называлось то же служебное слово, а истинная формулировка задачи (`GC`, свойство
`Problem.Description`) лежала в отдельной свёртке «Условие» — игрок читал два текста об одном
и том же и не находил в них цели.

**Решения.**

1. **Подпись списка — номер и название** (`ProblemViewModel.LabelOf`): «ts-001 · Спасти пять
   камней». Вид задачи и кю из подписи убраны: кю у всех встроенных задач одно и то же, а пометка
   о виде повторялась у каждой задачи. Слабая задача по-прежнему помечается («· слабая»): это
   характеристика качества контента, а не служебное слово.
2. **Формулировка задачи показывается целью** (`ProblemViewModel.GoalText`): берётся
   `Problem.Description` («Ход чёрных. Спасти пять камней: покажите три хода.»), а при её
   отсутствии — слова самой цели движка («убить группу» и т. п.). Свёртка «Условие» из
   `ProblemView.axaml` удалена вместе с `Expander` и его управлением в коде вида: условие и цель
   говорили об одном и том же.
3. **Служебные пометки удалены из интерфейса.** `ProblemGoal.Reference` больше не называет игроку
   вид задачи: его текст — «пройти линию решения» — остался только запасным, для задачи без
   формулировки (разбор SGF такие не принимает). Проверочный режим `--problems` печатает номер,
   название и цель задачи вместо столбца «решение источника / проверена движком».

**Почему так.** Цель задачи — то, что игрок должен сделать; происхождение решения (`GE[reference]`,
`SO`) — свойство задачи, а не её цель, и игроку оно ничего не даёт: принимается всё равно ровно
линия источника, и это видно по отказу хода. Единственное место, где о виде задачи сказано
в интерфейсе, — отказ «Это не решает задачу».

**Последствия.**
- Формулировки задач стали единственным текстом цели: правка `GC` в `Problems/*.sgf` сразу видна
  игроку, отдельного «условия» нет.
- Прежние пометки остались только в исторических записях (`PROBLEMS.md`, журнал решений) — там они
  объясняют, что и почему убрано.
- Живая приёмка режима «Задачи» нужна заново: подпись списка, цель и отсутствие свёртки проверяются
  глазами (стенд `tools/verify-ui2/verify-problems.ps1`).

**Проверка.** Сборка решения без предупреждений; домен **1133 пройдено + 2 пропущенных**,
приложение **644/644** (утилита `src/GoEngine.Tools.TestRunner`, логи `artifacts/t043-domain.txt`,
`artifacts/t043-app.txt`); двенадцать безоконных режимов и нагрузка — зелёные (код 0), в том числе
`--problems`. Живая приёмка на замороженной ревизии (стенд `tools/verify-ui2/verify-problems.ps1`,
14 проверок, 0 не прошло, журнал `artifacts/t043/live.log`): список показывает

   выходить ли из приложения.
8. **Настольная раскладка не перестроена**: строка режимов сверху, меню окна. Изменения в ней —

**Почему так.** Нижняя навигация — про разделы одного уровня; настройки и меню партии такими

## D-076. Обучение в игре: раздел «Обучение», уроки-данные и словарь терминов

**Дата:** 2026-10-07
**Статус:** принято (замечания пользователя 2026-10-07; T-045)

**Что не устраивало.** «Вот плейлист, видео с YouTube. Это ролики по 3-10 мин обучающие игре Го.
Ты работаешь в проекте — игра Го. Хочу перенести обучение непосредственно в игру. Не видео туда
монтировать, а обучение в игре. Я хочу сделать новую отдельную вкладку (аналогично "Задачи")…
Обучение на русском языке обязательно. + добавь глосарий, терминам игры го, которые применяются
в обучении».

**Источник материала.** Плейлист «обучение Го» из семи видео; расшифровки получены с YouTube
(`youtube-transcript-api`), разобраны и пересказаны по-русски:

| Видео | Что взято в игру |
|---|---|
| Урок 1 «Правила и цель игры» (7:58) | урок `go-01`: доска и пересечения, ход на пересечении, камни не двигаются, дыхания и плен, территория, группа |
| Урок 2 «Что такое глаза? Жизнь и смерть» (5:15) | урок `go-02`: глаз, запрещённый ход в глаз, второй глаз, «два глаза — жизнь» |
| Урок 3 «Партия 9×9. Подсчёт территории» (10:04) | урок `go-04`: забор и пространство, замкнутая стена, подсчёт, конец партии |
| Урок 4 «Атари Го. Лестница и двойное атари» (6:00) | урок `go-03`: атари, спасение камня, лестница, двойное атари |
| Урок 5 «Партия с комментариями», урок 6 «Нигири, фора и ранги», урок 7 «Где играть онлайн» | не перенесены: это не уроки-задания, а обзор партии, справка о рангах и обзор серверов |

**Решения.**

1. **Урок — это данные, а не код.** Сценарий урока лежит в файле (`Lessons/*.json` в
   `GoEngine.Problems`): шаги, тексты, позиции и принимаемые ходы. Движок (`LessonSession`)
   только исполняет сценарий, поэтому материал правится без правки кода и проверяется тестами
   как данные. Формат — тот же дух, что у задач: встроенные ресурсы сборки, значит работает
   и на Android.
2. **Два вида шагов.** Объяснение игрок читает и смотрит на позицию; задание он выполняет ходом
   по доске. Принимаемые ходы перечисляет автор урока, а не перебор: урок объясняет приём,
   и «правильных» ходов у него ровно столько, сколько задумано. Неверный ход позицию не меняет —
   как в задаче, игрок пробует снова.
3. **Ход в глаз — отдельный урок-запрет.** Шаг, где принимаемый ход запрещён правилами
   (самоубийство внутри глаза), зачитывается, а доска остаётся прежней: урок показывает не
   «неверно», а само правило. Так же объясняет это и видео.
4. **Позиции собираются легально** (`ProblemSetup`), точки записываются как в SGF
   (`dd` — четвёртая колонка, четвёртая строка сверху): формат знаком проекту, и ошибка
   в координате ловится сборкой, а не игроком.
5. **Раздел «Обучение» — четвёртый раздел оболочки.** На телефоне это четвёртая кнопка нижней
   навигации («Партия», «Задачи», «Обучение», «Меню»), в настольном окне — третья кнопка строки
   режимов, в общем меню — строка «Обучение» в группе «Режим». Уроки живут отдельным видом
   (`LessonView`), как задачи: та же доска, своя модель.
6. **Словарь терминов** (`Glossary/*.json`, 15 терминов): название по-русски, оригинал
   (японское или китайское слово) и объяснение по-русски со ссылками на уроки, где термин
   разбирается. Открывается кнопкой «Словарь терминов» в панели урока — вложенным экраном
   раздела «Обучение», как «О программе» у раздела «Меню».
7. **Обучение ведётся по-русски.** Тексты уроков и объяснения словаря — русские; оригинальные
   названия стоят рядом как справка. Это проверяется тестами: шаг без кириллицы роняет сборку.
8. **Подсветка точек доски.** Рендерер и `BoardControl` получили список подсвеченных точек
   (`HighlightPoints`): объяснение показывает, куда смотреть («вот этот глаз»), а не только
   называет это словами.

**Почему так.** Видео переносить нельзя, а методику — можно: ценность урока не в картинке,
а в порядке объяснений и в задании, которое игрок выполняет сам. Данные вместо кода выбраны
потому, что курс будет расти, а движок — нет. Ход в глаз и запрещённые ходы — то место, где
обучение обязано показать правило руками игрока: без этого «глаз» остаётся словом.

**Последствия.**
- В игре 4 урока, 19 шагов, из них 8 заданий; словарь 15 терминов.
- Прогресс между запусками не сохраняется: урок проходится за один сеанс. Это следующий шаг,
  если курс будет расти.
- Уроки 5–7 плейлиста не перенесены: партия с комментариями, нигири/фора/ранги и обзор серверов
  в интерактивный урок не укладываются. Ранги и фора есть в самой игре (уровни и коми).
- Живой стенд `tools/verify-ui2/verify-lessons.ps1` проверяет раздел, шаг, ход по доске
  и словарь.

**Проверка.** Сборка решения без предупреждений; домен **1161 пройдено + 2 пропущенных**,
приложение **723/723**; полный `./check.ps1` с нагрузкой — зелёный, код 0. Живая приёмка на
замороженной ревизии (стенд `tools/verify-ui2/verify-lessons.ps1` со сборкой, 11 проверок,
0 не прошло, журнал `artifacts/verify-ui2/lessons.log`): раздел «Обучение» открывает урок
«go-01 · Правила и цель игры», шаг 1 из 7; «Далее» ведёт к шагу 2; щелчок по центру доски
принимается уроком — «Верно! Камень занял пересечение и останется на нём до конца партии»;
словарь открывается и объясняет термины по-русски («Атари», «Глаз», «Дыхание»); «Назад»
возвращает к уроку, «Заново» — к первому шагу. Снимки: `artifacts/verify-ui2/lesson-start.png`,
`lesson-task.png`, `lesson-answer.png`, `lesson-glossary.png`.

## D-077. Уроки тактики: территория вместо погони, форма групп, ко

**Дата:** 2026-10-07
**Статус:** принято (замечание пользователя 2026-10-07; T-046)

**Что не устраивало.** «Не хватает обучения тактики игры, необходимо добавить как минимум
следующими 3-мя уроками. Взять за основу показ партии по ссылке… И доработать \ добавить \
расширить ещё. Потому что новички часто страдают тем, что гоняются за съеденными камнями,
а не за территорией. Необходимо обучить… после базовых 4-х уроков, уже реализованных».

**Источник материала.** Видео 5 плейлиста — «Партия Го с комментариями. В этот раз сложнее!»
(`erRjKpAvLtk`). Из расшифровки взяты приёмы, которые автор показывает на партии:

| Что в видео | Куда попало |
|---|---|
| «Белый камень на второй линии — спасти его не получится… если спасти камень не получается, его придётся бросить» | `go-05`, шаг «Обречённый камень бросают» |
| «Большинство игроков просто сделало бы ход сюда, чтобы защитить угол, но белые идут на обмен» | `go-05`, шаг «Погоня или большой ход» |
| «Чёрные не потратили ни одного дополнительного хода на захват трёх камней… эти камни уже мертвы… захватывать их — уменьшать свою же территорию» | `go-05`, шаг «Мёртвые камни снимаются сами» |
| «Белые хотят отрезать чёрные камни справа… белые кое-что выпускают из виду»; чёрные соединяются | `go-07`, задания «Соедините свои камни» и «Разрежьте соперника» |
| «Из-за того что в углах скрыта особая магия, белые не могут здесь соединиться… иначе чёрные одним ходом захватят их все» | `go-07`, шаг «В углу соединиться труднее» |
| «Правило ко запрещает повторение предыдущей позиции… нужен отвлекающий ход, угроза» | `go-08`, шаги «Правило ко», «Захват и ответ», задание «Сыграйте угрозу» |
| «Первым ходом чёрные занимают центр… он даёт инициативу» и совет переходить на 13×13 после правил | `go-06`, урок об углах, сторонах и центре |

**Решения.**

1. **Четыре новых урока** (вместо минимальных трёх), все — данные, как и первые четыре:
   `go-05` «Территория важнее погони» (5 шагов), `go-06` «Угол, сторона, центр» (4 шага),
   `go-07` «Соединение и разрезание» (4 шага), `go-08` «Ко и угрозы» (4 шага). Вместе с базовыми
   четырьмя — 8 уроков, 36 шагов, из них 15 заданий на доске.
2. **Главная мысль — очки приносит территория, а не камни.** Урок `go-05` ставит перед игроком
   выбор из двух подсвеченных ходов: атака на мертвые камни против большого хода. Неверный ход
   отклоняется с объяснением, почему погоня проигрышна, — это ответ на жалобу «новички гоняются
   за съеденными камнями».
3. **Выбор из двух ходов — новый приём в уроке**, не новый вид шага: подсветка показывает
   кандидатов, а принимаемый ход один. Так учат не правилу, а решению.
4. **Форма групп и ко** — то, что новичок не выводит из правил сам: соединение и разрезание
   (`go-07`) объясняют, почему разрезанная группа слаба, а `go-08` показывает последнее правило
   игры и приём «угроза важнее ко». Оба урока опираются на моменты разобранной партии.
5. **Словарь вырос вместе с курсом:** 24 термина (было 15). Добавлены «Ко», «Угроза»,
   «Соединение», «Разрезание», «Обмен», «Мёртвые камни», «Угол», «Сторона», «Первая линия»;
   у каждого — русское объяснение, оригинал и ссылка на урок, где термин разбирается.

**Почему так.** Первые четыре урока отвечают на вопрос «как играют», тактические — на вопрос
«куда играть и что считать выгодным». Именно на нём новички и теряют партии: правила они знают,
а привычка гнаться за камнями остаётся. Поэтому уроки тактики построены не на теории, а на
позициях-выборах: игрок сам решает, какой ход больше принесёт, и сразу видит разбор.

**Найдено живым прогоном.** Первая версия уроков читала точки SGF с перевёрнутой строкой
(«a» — верхняя строка файла, а внутри приложения строка считалась снизу вверх). В приложении
это не так: рендер рисует <c>Point.Y</c> сверху вниз, номера строк на доске идут сверху вниз
(D-009), и игровой <c>SgfReader</c> читает SGF без переворота. Из-за расхождения позиции уроков
рисовались зеркально по вертикали: «нижний край» оказывался верхним. Разбор уроков приведён
к конвенции игры (`LessonJson.PointOf` строку не переворачивает), тексты перепроверены по снимку,
тест на разбор точки переписан на новую конвенцию. Замечание относится к 0.2.58: выпуск 0.2.59
содержит исправление.

**Последствия.**
- Курс идёт по порядку: правила (go-01…go-04) → тактика (go-05…go-08). Порядок задан
  идентификаторами, список уроков в разделе «Обучение» показывает их по порядку.
