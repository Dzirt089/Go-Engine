# 06. Выпуск и качество

## Как устроен CI/CD

| Workflow | Когда | Что делает |
|---|---|---|
| `ci.yml` | push в `main`, pull request | Linux: сборка, `dotnet test`, все проверочные режимы; Windows: `./check.ps1 -SkipStress` |
| `latest.yml` | push в `main` | версия `0.2.<run_number>`, сборка настольных платформ и APK, публикация плавающего релиза `latest` и `update.json` |
| `build.yml` | вызывается из `latest.yml`/`release.yml` | общая сборка: Windows/Linux/macOS + Android APK (подпись через секреты) |
| `release.yml` | версионированный выпуск | неизменяемый релиз `v0.2.<N>` с теми же артефактами |

Схема: **push в `main` → CI проверяет → Latest build собирает и публикует**.
Отдельного «релизного» коммита нет: выпуск — это следствие пуша.

## Версионирование

- версия приложения: `0.2.<github.run_number>` (например `0.2.106`);
- `versionCode` для Android — тот же `run_number` (целое, только растёт);
- тег: `v0.2.<run_number>`; подпись Android — из секретов репозитория;
- APK в выпуске: `com.goengine.app-Signed.apk` (~132 МБ). Неподписанные APK в релиз не попадают.

## Манифест обновления

`releases/download/latest/update.json` — постоянный адрес, который знает приложение:

| Поле | Смысл |
|---|---|
| `version` | версия выпуска |
| `commit` | коммит сборки (короткий хеш) |
| ссылки на файлы | откуда скачивать (APK/установщики) |

Проверка обновления в приложении — `App/Services/Updates`; режим без окна — `--update`.

## Обязательная приёмка перед выпуском (урок 0.2.105)

> 0.2.105 собралась, тесты были зелёные, но приложение **зависло на стартовой картинке** на
> телефоне. Причина — старт-рискованный рефакторинг (единая оболочка + edge-to-edge), который
> не проверили на устройстве до публикации. Правило появилось после этого случая.

Порядок:

1. `./check.ps1` — зелёный (сборка без предупреждений, оба набора тестов, все режимы).
2. Собрать APK (CI) и **поставить на эмулятор/устройство до публикации**.
3. Запустить приложение: дождаться замены экрана загрузки на оболочку (не «Готовлю нейросеть» вечно).
4. Пройти смоук: партия (несколько ходов, пас, закончить партию, счёт), задачи (1–2), обучение (1 урок),
   настройки (переключение системы счёта), меню.
5. Проверить поворот/перезапуск (пересоздание активности) — не должно быть падения.
6. Только после этого пушить в `main` (пуш и запускает публикацию).
7. После публикации поставить APK **из релиза** и повторить шаг 3.

## Чек-лист выпуска

- [ ] `./check.ps1` зелёный;
- [ ] версия в «О программе» совпадает с манифестом `update.json`;
- [ ] APK из релиза ставится и запускается на чистом устройстве;
- [ ] пройден смоук (партия, задача, урок, настройки);
- [ ] нет падений в логе (`FATAL`/`AndroidRuntime`);
- [ ] `DECISIONS.md` дополнен решением о выпуске (если менялось поведение);
- [ ] оба remote обновлены: `git push origin main` и `git push github main`.

## Откат

Если выпуск сломан:

1. `git revert <коммит>` (или откат конкретных файлов: `git checkout <хороший-коммит> -- <файлы>`);
2. `./check.ps1`;
3. собрать и проверить APK на эмуляторе;
4. push в `main` — CI выпустит новый номер версии;
5. в `DECISIONS.md` записать причину и что именно откатили.

## Процесс качества

1. **Тесты** — домен и приложение (см. `05-development.md`).
2. **Проверочные режимы без окна** — 16 режимов, все в `check.ps1` и CI.
3. **Живые прогоны QA-агентами** — два типа:
   - «новичок»: можно ли научиться играть по приложению, где застревает;
   - «дан-5»: все этапы (задачи, уроки, партии, счёт) на соответствие правилам.
   Прогоны идут на отдельных AVD, чтобы не мешать друг другу; отчёты — `artifacts/qa*/report.md`.
4. **Ревизия содержания** — отдельный проход по файлам содержания (задачи/уроки/партии).
5. Находки фиксируются, исправляются и **проверяются повторным прогоном** на уже собранном APK.

Правило приёмки: исправление считается закрытым только после повторной проверки на выпуске,
где оно есть (а не на предыдущем APK).
