# 06. Выпуск и качество

## Как устроен CI/CD

| Workflow | Когда | Что делает |
|---|---|---|
| `ci.yml` | push в `main`, pull request | Linux: сборка, `dotnet test`, все проверочные режимы; Windows: `./check.ps1 -SkipStress` |
| `latest.yml` | push в `main` | версия `0.2.<run_number>`, сборка настольных платформ и APK, публикация плавающего релиза `latest` и `update.json` |
| `build.yml` | вызывается из `latest.yml`/`release.yml` | общая сборка: Windows/Linux/macOS + Android APK (подпись через секреты) |
| `release.yml` | push тега `vX.Y.N` или вручную из Actions | версия `X.Y.N` и `versionCode` `N` из тега; сборка через `build.yml` с суффиксом `-vX.Y.N`; публикация или обновление релиза тега |

Схема: **push в `main` → CI проверяет → Latest build собирает и публикует**.
Отдельного «релизного» коммита нет: выпуск — это следствие пуша.

Версионированная веха (`release.yml`) — отдельный канал: её запускают тегом или вручную,
когда нужен неизменяемый выпуск с собственным номером; см. «Версионированный релиз по тегу».

## Версионирование

Версию каждому каналу задаёт свой источник:

| Канал | Workflow | Версия | `versionCode` Android | Тег |
|---|---|---|---|---|
| плавающий `latest` | `latest.yml` (push в `main`) | `0.2.<run_number>` | `run_number` | `v0.2.<run_number>` |
| версионированная веха | `release.yml` (тег или вручную) | `X.Y.N` из тега | `N` из тега | `vX.Y.N` |

- подпись Android — из секретов репозитория;
- APK в выпуске: `com.goengine.app-Signed.apk` (~132 МБ). Неподписанные APK в релиз не попадают.

## Версионированный релиз по тегу

`release.yml` собирает веху из тега. Версия и `versionCode` вычисляются из тега `vX.Y.N`
отдельной job «Версия релиза» и передаются в `build.yml`, который кладёт их внутрь сборок:
`-p:Version=` — настольным приложениям и установщику, `-p:ApplicationDisplayVersion` и
`-p:ApplicationVersion` — Android. Имена архивов получают суффикс `-vX.Y.N`, например
`go-engine-win-x64-v0.2.138.zip`. Без такой передачи сборка осталась бы с версией проекта
по умолчанию (`1.0.0` в приложении, `1.0`/1 в APK), и обновление с вехи не встало бы
поверх установленной программы.

Запуск:

- **по тегу** — тег должен указывать на нужный коммит: `git tag v0.2.138` и
  `git push origin v0.2.138`; workflow стартует сам;
- **вручную** — Actions → **Release** → **Run workflow**: в поле `tag` — `v0.2.138`,
  при необходимости флажок `draft` (черновик не виден для скачивания до публикации).
  Если такого тега ещё нет, `gh` создаст его от головы ветки по умолчанию; надёжнее поставить
  тег на нужный коммит и запускать релиз его push'ем.
- **важно про ручной запуск** — checkout берёт выбранную ветку (обычно `main`), а не тег:
  так выпускают веху из текущего `main`, но пересобрать старый тег этим способом нельзя —
  в релиз уйдёт сборка ветки. Точный коммит тега собирается только запуском по push тега.

Требования к тегу:

- строго `vX.Y.N` из трёх целых чисел (`v0.2.138`); суффиксы и ведущие нули не принимаются —
  версия в приложении должна совпадать с тегом;
- `N ≥ 1`: `versionCode` в Android обязан быть положительным;
- схема `versionCode = N` рассчитана на ветку `0.2.x`; для будущего `1.x` понадобится отдельная
  политика `versionCode` — иначе номер версии Android не будет расти;
- `N` не меньше `versionCode` установленной сборки. У плавающего `latest` это `run_number`
  последнего пуша, поэтому для вехи берут `N` не меньше номера последнего выпуска `latest`;
  иначе Android не поставит веху поверх более новой установленной версии (обходной путь —
  чистое устройство).

Повторный запуск на существующем теге безопасен: релиз не создаётся заново, а его файлы
удаляются и загружаются снова (`gh release delete-asset` → `gh release upload`; `--clobber`
на существующем релизе отдаёт «ReleaseAsset.name already exists», как и в `latest.yml`).
Порядок шагов: `check.sh` → сборки `build.yml` → создание или обновление релиза. Веха
не становится «Latest» на GitHub (`--latest=false`): главным свежим релизом остаётся
плавающий `latest`, на который указывает `update.json`.

**Совмещение с плавающим latest.** Оба канала используют одно пространство тегов
`v0.2.<N>`: тег `latest` — `v0.2.<run_number>`, тег вехи — `v0.2.<номер>`. Поэтому
безопасный порядок выпуска вехи такой: сначала push в `main` публикует версию
`v0.2.N`, затем тот же тег/релиз пересобирается через `release.yml` как веха
(архивы получают суффикс `-v0.2.N`, номер версии и `versionCode` те же). Если поставить
тег на номер, который `latest` ещё не выпускал, следующий push с этим `run_number`
дополнит тот же релиз своими файлами; версия при этом совпадает, но «неизменяемой» веха
становится только после того, как номер пройден плавающим каналом.

## Манифест обновления

`releases/download/latest/update.json` — постоянный адрес, который знает приложение:

| Поле | Смысл |
|---|---|
| `version` | версия выпуска |
| `commit` | коммит сборки (короткий хеш) |
| ссылки на файлы | откуда скачивать (APK/установщики) |

Проверка обновления в приложении — `App/Services/Updates`; режим без окна — `--update`.

## Обязательная приёмка перед выпуском (урок 0.2.105)

> 0.2.105 собралась, тесты были зелёные, но приложение **зависло на стартовой картинке** на
> телефоне. Причина — старт-рискованный рефакторинг (единая оболочка + edge-to-edge), который
> не проверили на устройстве до публикации. Правило появилось после этого случая.

Порядок:

1. `./check.ps1` — зелёный (сборка без предупреждений, оба набора тестов, все режимы).
2. Собрать APK (CI) и **поставить на эмулятор/устройство до публикации**.
3. Запустить приложение: дождаться замены экрана загрузки на оболочку (не «Готовлю нейросеть» вечно).
4. Пройти смоук: партия (несколько ходов, пас, закончить партию, счёт), задачи (1–2), обучение (1 урок),
   настройки (переключение системы счёта), меню.
5. Проверить поворот/перезапуск (пересоздание активности) — не должно быть падения.
6. Только после этого пушить в `main` (пуш и запускает публикацию).
7. После публикации поставить APK **из релиза** и повторить шаг 3.
8. **R-001 (после 0.2.123):** на реальном устройстве при живом процессе выполнить
   `adb shell am start -W -n <MainActivity> -f 0x18000000` три раза — не должно быть
   `FATAL EXCEPTION`/`already has a visual parent`/Application Error; в логе должна быть строка
   «Пересоздание Activity в живом процессе … главный вид отвязан True». После каждого повтора —
   обычный запуск. Сценарий на AVD Android 15 не воспроизводится, проверять на реальном Android 12.
9. **Back-матрица (R-002):** Home (подтверждение выхода), Партия с ИИ и Обучение (→ Home,
   партия сохраняется), Меню (→ предыдущий раздел), лобби (закрывается), активная сетевая
   (подтверждение «Выйти из сетевой игры?»), диалоги/шторка/ComboBox.
10. **Тема (R-003):** Home 360 dp в светлой и тёмной темах — заголовок и подпись карточки
    «Партия с ИИ» читаются (контраст ≥4.5:1), остальные карточки без регрессий.

## Чек-лист выпуска

- [ ] `./check.ps1` зелёный;
- [ ] версия в «О программе» совпадает с манифестом `update.json`;
- [ ] APK из релиза ставится и запускается на чистом устройстве;
- [ ] пройден смоук (партия, задача, урок, настройки);
- [ ] нет падений в логе (`FATAL`/`AndroidRuntime`);
- [ ] `DECISIONS.md` дополнен решением о выпуске (если менялось поведение);
- [ ] оба remote обновлены: `git push origin main` и `git push github main`.

## Откат

Если выпуск сломан:

1. `git revert <коммит>` (или откат конкретных файлов: `git checkout <хороший-коммит> -- <файлы>`);
2. `./check.ps1`;
3. собрать и проверить APK на эмуляторе;
4. push в `main` — CI выпустит новый номер версии;
5. в `DECISIONS.md` записать причину и что именно откатили.

## Процесс качества

1. **Тесты** — домен и приложение (см. `05-development.md`).
2. **Проверочные режимы без окна** — 16 режимов, все в `check.ps1` и CI.
3. **Живые прогоны QA-агентами** — два типа:
   - «новичок»: можно ли научиться играть по приложению, где застревает;
   - «дан-5»: все этапы (задачи, уроки, партии, счёт) на соответствие правилам.
   Прогоны идут на отдельных AVD, чтобы не мешать друг другу; отчёты — `artifacts/qa*/report.md`.
4. **Ревизия содержания** — отдельный проход по файлам содержания (задачи/уроки/партии).
5. Находки фиксируются, исправляются и **проверяются повторным прогоном** на уже собранном APK.

Правило приёмки: исправление считается закрытым только после повторной проверки на выпуске,
где оно есть (а не на предыдущем APK).
