# 02. Домен: правила го, доска, счёт

> Источник истины по правилам — `GO_RULES.md`. Этот документ объясняет, **как правила
> реализованы в коде** и на какие грабли наступают новички.

## Координаты — первое, что нужно понять

В проекте две системы координат, и они не совпадают:

| Где | Как | Пример |
|---|---|---|
| Подпись на доске (`BoardCoordinates.Label`) | буква столбца без `I`, номер строки **сверху вниз** | `D4` |
| SGF (`a`–`s`) | `a` = первый столбец, `a` = первая строка **в формате SGF** | `dd` |

- Буква `I` пропускается: столбцы `A B C D E F G H J K L M N O P Q R S T`.
- `Point(x, y)`: `x` — столбец, `y` — строка; строка 1 в подписи — верхняя (D-009).
- **Задачи (`ProblemSgf`) переворачивают строки SGF**: файл `ts-*.sgf` читается с переворотом,
  поэтому буквы SGF и подписи доски различаются. Если правите SGF — сверяйтесь с доской в приложении,
  а не с буквами файла.
- Уроки и разборы (`LessonJson`, `ReviewJson`) читаются **сверху вниз**, как подпись доски.

Практическое правило: любую координату из текста проверяйте в приложении и тестом по позиции,
а не «на глаз» по SGF.

## Доска

- `Board` — иммутабельная: `ApplyMove(Move)` возвращает новую доску. Внутри — плоский
  `StoneColor[size*size]`; наружу массив не отдаётся.
- `CapturedStones` — результат последнего `ApplyMove`, только чтение.
- Для перебора (MCTS) — `Clone()` + `MakeMove(Move)`: мутация на месте ради скорости. В прикладном
  коде используйте иммутабельный путь.
- `GroupTracker` поддерживает группы и дыхания. Сложные места (группы, снятия, ко) обязаны быть
  объяснены в коде — требование Style Bible.
- `BoardSize` — `9`, `13`, `19`; `Komi` — `readonly record struct`.

## Легальность хода

`MoveLegality` + `GameState.TryPlay` возвращают `MoveResult`/`Result`:

| Исход | Как сообщается |
|---|---|
| нелегальный ход (занято, самоубийство) | `Result` с ошибкой, без исключения |
| ко | `KoRule` + `PositionHistory`/`PositionHash` |
| конец партии | `GameStatus` |

Снятие камней — `CaptureResolver`; снятые камни попадают в счёт как пленные.

## Счёт

`ScoringRule` — два значения-`Enumeration`:

- **японская (по умолчанию):** очки = территория + пленные + камни, снятые как мёртвые, плюс коми белым;
- **китайская:** очки = свои камни на доске + территория; пленные не считаются.

Считают `Scorer` → `FinalScore`, мёртвые группы ищет `DeadGroupSearch` (их помечает перебор,
а не игрок — D-070/D-084), разбор чисел — `AreaBreakdown`. `FinalScore` умеет и `TerritoryMargin`,
и `AreaMargin`; победитель берётся по **выбранной** системе.

Правила, которые нельзя нарушать:

1. Система счёта — **из настроек партии**, а не «всегда площадь». Смена системы пересчитывает
   и завершённую партию.
2. Позиция, где сторона не поставила ни камня, считается **недоигранной**: территория не начисляется,
   победитель не называется (D-115).
3. Нейтральные точки (дамэ) не засчитываются никому.
4. Коми задаётся настройками партии; типичное турнирное — 6,5 на 19×19, 5,5 на 9×9.

Разбор чисел для игрока — `MainViewModel.ScoreJapanese` / `ScoreChinese` / `ScoreDetail`.

## Жизнь и смерть, формы

- `ProblemLife` — оценка групп: дыхания, глаза (строгий критерий: пустая область, окружённая только
  этой группой, куда соперник не может войти легально), `CountEyes`, `LifeVerdict`.
- `MoveShape` — распознавание форм хода: ноби, косуми, кейма, тоби, бамбук, пасть тигра, кирпич,
  пустой треугольник и т. д. Важно: `ShapeFacts.Points` обязан содержать **все** камни формы
  (бамбук — четыре, кирпич — четыре, пасть тигра — три), иначе подсветка обводит только соседей хода.
- `ShapeSet` — набор форм хода (до трёх), глобальная дедупликация по имени, подключение групп.
- Плохие формы в «Формах решения» не показываются: решение не должно подаваться как «правильная форма».

## Задачи: проверка цели

- Задачи из источника помечены `GE[reference]`: линия эталонная, **машинного доказательства исхода нет**
  (`PROBLEMS.md`). Поэтому цель обязана формулироваться по тому, что линия реально доказывает:
  «разрушить глазную форму», «оставить один глаз», «зажать группу», а не «убить», если снятия нет.
- `ProblemGoalCheck`/`ProblemSession` проверяют ходы и вердикт; `ProblemStrategy`/`ProblemTexts`
  объясняют смысл — они статические, поэтому обязаны сверяться с финальной позицией тестами
  (`ProblemContentTests`).
- Посторонний ход должен отклоняться, правильный — приниматься (проверены 36/36 задач).

## Партии-разборы и уроки

- `ReviewSession` — разбор: заметки (`ReviewNote`) и вопросы (`ReviewQuiz`) привязаны к номеру хода
  `before`; вопрос обязан стоять за ту сторону, чей ход, и не называть ответ в заголовке/тексте.
- `MoveDescriber` — автоматические пояснения к ходу: `State(...)` (дыхания, размер группы, враг)
  и `Intent(...)` с вариантами формулировок. Текст не должен утверждать «разрезаю», если ход лишь
  примыкает к двум группам, и «соединяю», если группа одна.
- Уроки — `LessonSession`: шаги-объяснения и шаги-задания; ответ сверяется с `LessonStep.Answer`.
  Верный ход принимается, неверный отклоняется с объяснением **по делу**.

## Как читать доменные тесты

`src/GoEngine.Tests` — живая документация правил: имена тестов на русском описывают сценарий.
Начинайте с `Board`, `Scoring`, `Rules`, `Problems` — там зафиксированы договорённости,
на которые можно ссылаться в обсуждении.

## Частые ошибки

1. Сравнивать SGF-буквы с подписью доски без учёта переворота строк.
2. Считать «дыхания» по соседям, не учитывая группы и снятия.
3. Считать площадь там, где выбрана японская система (и наоборот).
4. Писать в тексте задачи/урока координату, которую надо найти (спойлер).
5. Объявлять «убить/спасти», когда линия этого не доказывает.
6. Забыть, что `default(Point)` — валидная точка `(0,0)`, а не «нет значения».
